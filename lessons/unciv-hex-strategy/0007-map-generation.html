地图生成流水线

第六课给了你一个装地块的容器，这一课看一张真正的世界怎样被造出来：从开局按钮出发，MapGenerator 按什么顺序跑完十几道工序，新游戏和地图编辑器在哪里分岔，以及一个 seed 到底能保证什么、不能保证什么。读完你应当能按依赖排出生成阶段，说出两种分支的差别，并界定 seed 的可复现范围。

需要的基础：第三课的规则集与 unique、第六课的 TileMap 与地块分层。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标、回顾与场景

先给三个场景。场景一：新游戏界面点“开始”，几秒后一张有大陆、河流、资源和出生点的地图出现。场景二：地图编辑器点“生成”，同一套管线跑一遍，但地图上不会摆出生点。场景三：主菜单背景里缓缓滚动的世界，也是这套管线悄悄生成的。三个入口，一套生成器。

先回顾第六课，两个口述问题

本课的三个问题

  • 阶段与顺序：一张地图要经过哪些工序？谁必须排在谁前面？
  • 两个分支：新游戏生成和编辑器生成，共用哪些阶段、各有哪些专属步骤？
  • 随机性边界：同一个 seed 重开会得到什么、不会得到什么？

读完还要会一件事：不看正文，把打乱的地形阶段排回源码顺序，并解释两处依赖关系。

口述两个关键结论

  1. 第六课的环绕补偿向量 (r, −r) 为什么能保持 x+y 不变？它改变了什么？
  2. 相邻两块地之间的公共边是条河，查询时读哪块地的哪个字段？（B 在 A 的右上）

这两条是第六课“环绕”与“河流边存储”的核心，本课第 4 节谈 seed 时还会用到“同一条链、同一批数据”的想法。

1. 开局按钮怎样请出地图生成器

新游戏的入口在 GameStarter。它的类注释直接给出了本课的随机性结论，接着的 init 块按顺序组装规则集、文明和地图。先看注释与地图相关的那一段：

// GameStarter.kt 类注释（开头部分）：
// 地图地形是确定的，但开局设置——包括出生点、资源和其他细节——是随机的，
// 依据 GameContext.stateBasedRandom，而它基于每局完全随机的 gameId。
class GameStarter private constructor(
    private val gameSetupInfo: GameSetupInfo
) {
    // …companion 与字段省略…
    init {
        // 组规则集（第三课）；先备好地图生成器
        ruleset = RulesetCache.getComplexRuleset(gameInfo.gameParameters)
        val mapGen = MapGenerator(ruleset)

        // 生成新地图（部分代码；载入已有地图的分支省略）
        } else runAndMeasure("generateMap") {
            // 生成器需要知道有哪些文明，才能生成区域、出生点和资源
            phaseOneChosenCivs = chooseCivilizations(existingMap = false)
            addCivilizations(phaseOneChosenCivs)
            tileMap = mapGen.generateMap(gameSetupInfo.mapParameters,
                gameSetupInfo.gameParameters, gameInfo)
            tileMap.mapParameters = gameSetupInfo.mapParameters
            // 先暂时忘掉它们！生成可能放不下某些城邦，稍后用旧方法兜底重放
            gameInfo.civilizations.clear()
        }
    }
}

类注释先立结论：地形（terrain）是确定的，由种子决定；开局设置（出生点、资源等）随机，依据 stateBasedRandom，而这个随机又基于每局完全随机的 gameId。本课第 4 节会验证这段话的每一半。

init 里先按第三课的方法组出复杂规则集，再 MapGenerator(ruleset)。注意生成器的构造参数只有规则集（和可选的协程作用域）——它不保存地图、不保存种子，输入输出全部走方法。

生成地图之前，先 chooseCivilizations 选好文明并 addCivilizations 挂进 gameInfo——注释说明了原因：生成器要知道文明数量，才能算区域和出生点。生成完立刻 clear，因为生成时可能放不下某些城邦，稍后要用旧方法兜底重放。

generateMap 收到三样东西：mapParameters（形状、大小、环绕、seed 与各强度参数）、gameParameters（文明数等整局设置）、gameInfo（整局状态）。最后两个参数带默认值，可以不给。

同一个生成器为三个入口服务。区别只在于传不传 gameInfo、传不传协程作用域：

调用方场景传 gameInfo 吗传协程作用域吗
GameStarter新开一局传（已挂文明）不传
MapEditorGenerateTab编辑器整图/分步生成不传不传
MainMenuScreen主菜单背景图不传传（可中止）

主菜单背景在 startBackgroundMapGeneration 里造一张矩形 pangaea 图，把协程作用域传给生成器——第 2 节会看到它被 runAndMeasure 用来随时中止。传不传 gameInfo，正是第 3 节两条分支的分水岭。

2. generateMap 的十几道工序

打开 MapGenerator.generateMap。先看入口——它在真正开工前做了五步准备。代码里的 ①～⑤ 与右侧讲解一一对应：

// MapGenerator.generateMap（入口部分代码）：开工前的五步准备。
fun generateMap(mapParameters: MapParameters,
        gameParameters: GameParameters = GameParameters(),
        gameInfo: GameInfo? = null): TileMap {

    val mapType = mapParameters.type

            tile.baseTerrain = Constants.ocean
            tile.setTerrainTransients()

① 处理 seed：默认值 0 表示“玩家没选种子”，换成当前毫秒数；非 0 就原样用。

② seedRNG 用这个 seed 重置生成器自带的随机源——从这一刻起，后面所有阶段的随机数都从同一个序列里取，这是“同 seed 同地图”的根基。

⑤ 提前出口：MapType.empty 把整张图改成海洋直接返回，一个阶段都不跑。空地图是编辑器手工画图的起点。

runAndMeasure 有两个职责。平时它只是直接执行 action；打开 consoleTimings 调试开关才打印各阶段耗时；此外它在协程作用域已取消时直接跳过——主菜单背景图生成传了作用域，窗口重开时旧任务就被丢弃。

// MapGenerator.runAndMeasure（相关代码）：计时 + 中止检查。
private fun runAndMeasure(text: String, action: ()->Unit) {
    if (coroutineScope?.isActive == false) return
    if (!consoleTimings) return action()
    val startNanos = System.nanoTime()
    action()
    val delta = System.nanoTime() - startNanos
    debug("MapGenerator.%s took %s.%sms", text, delta/1000000L, (delta/10000L).rem(100))
}

第一行是中止检查：作用域不再活跃就不执行该阶段。第二行是计时的开关，consoleTimings = false 时直接跑 action，一行开销都没有。

所以生成器平时完全不计时；只有调试开关打开时才测每个阶段的耗时。这个开关在 GameStarter 里也有一份同样的实现。

3. 新游戏与编辑器：同一条链，两处岔路

地形阶段跑完后，generateMap 按“这是不是编辑器”分岔。判定只看文明列表：

// MapGenerator.generateMap（分支部分代码）：
// 基于区域的生成——地图编辑器生成时不用
val civilizations = gameInfo?.civilizations
val isMapEditor = civilizations?.isEmpty() ?: true
if (! isMapEditor) {
    map.gameInfo = gameInfo
    val regions = MapRegions(ruleset)
    runAndMeasure("generateRegions") {
        regions.generateRegions(map, civilizations.count { ruleset.nations[it.civName]!!.isMajorCiv })
    }
    runAndMeasure("assignRegions") {
        regions.assignRegions(map,
            civilizations.filter { ruleset.nations[it.civName]!!.isMajorCiv }, gameParameters)
    }
    // 奇观必须在多数资源之前——两者之间要求最小距离
    runAndMeasure("NaturalWonderGenerator") {
        NaturalWonderGenerator(ruleset, randomness).spawnNaturalWonders(map)
    }
    runAndMeasure("placeResourcesAndMinorCivs") {
        regions.placeResourcesAndMinorCivs(map,
            civilizations.filter { ruleset.nations[it.civName]!!.isCityState })
    }
} else {
    runAndMeasure("NaturalWonderGenerator") {
        NaturalWonderGenerator(ruleset, randomness).spawnNaturalWonders(map)
    }
    // 兜底的直铺资源——地图编辑器生成时用
    runAndMeasure("spreadResources") { spreadResources(map) }
}
runAndMeasure("spreadAncientRuins") { spreadAncientRuins(map) }

if (isMapEditor)
    mirror(map)

// 生成可能产生规则集不认可的地形/特征组合
for (tile in map.values)
    TileNormalizer.normalizeToRuleset(tile, ruleset)

return map

判定只有一行：gameInfo?.civilizations?.isEmpty() ?: true。没传 gameInfo（编辑器、主菜单背景）或文明列表为空，就按编辑器处理。第一课讲过 GameStarter 生成前先把文明挂进 gameInfo，所以新游戏必然走进第一条岔路。

新游戏分支用 MapRegions 生成并分配区域（每家的出生地带），再放奇观、再放资源与城邦。奇观必须在多数资源之前的注释给出了依赖：两者之间要求最小距离，先放的要先占位置。这些是第 10 课“可玩的出生地与资源”的主场。

编辑器分支不跑区域，改用 spreadResources 把资源直接铺在符合条件的格子上。两条岔路汇合后一起铺古代遗迹；编辑器分支再多一步 mirror（镜像设置生效时才真正复制）。

最后的 TileNormalizer.normalizeToRuleset 是收尾防线：前十几个阶段可能拼出规则集不认可的地形/特征组合，这里逐格校正，保证产出永远符合规则集约定。

编辑器还有一个“分步生成”入口：把阶段链拆成单步重跑。对应 generateSingleStep 和编辑器里的步骤枚举：

// MapGenerator.generateSingleStep（部分代码）：只重跑一步。
fun generateSingleStep(map: TileMap, step: MapGeneratorSteps) {
    if (map.mapParameters.seed == 0L)
        map.mapParameters.seed = System.currentTimeMillis()

    randomness.seedRNG(map.mapParameters.seed)

    runAndMeasure("SingleStep $step") {
        when (step) {
            MapGeneratorSteps.None -> Unit
            MapGeneratorSteps.All -> throw IllegalArgumentException(
                "MapGeneratorSteps.All cannot be used in generateSingleStep")
            MapGeneratorSteps.Landmass -> MapLandmassGenerator(map, ruleset, randomness).generateLand()
            MapGeneratorSteps.HumidityAndTemperature -> applyHumidityAndTemperature(map)
            MapGeneratorSteps.Elevation -> MapElevationGenerator(map, ruleset,
                terrainConditions, randomness).raiseMountainsAndHills()
            // …其余步骤同阶段链顺序…
            MapGeneratorSteps.Rivers -> {
                val resultingTiles = mutableSetOf<Tile>()
                RiverGenerator(map, randomness, ruleset).spawnRivers(resultingTiles)
                convertTerrains(resultingTiles)
            }
            MapGeneratorSteps.Resources -> spreadResources(map)
            MapGeneratorSteps.AncientRuins -> spreadAncientRuins(map)
        }
    }
}

Unciv 的生成器不碰界面：输入是参数对象，输出是改好的 TileMap，三个入口共用。移植时可以保留这种“阶段函数”形态——每步是 (地图, 规则集, 随机源) → 改地图，编辑器就能复用同一批步骤做预览。在 Godot 里，生成阶段只写数据；Tiles / 节点等画面表现等数据定稿后再建，避免每改一步就重建一遍场景树。分步重跑还提醒我们：每一步的输入要明确，否则“重跑第 5 步”可能因为第 4 步已变而产生不同结果。

4. seed 能保证到哪一步

第 2 节说“同 seed 同地图”。这句话有边界，边界就藏在随机源的归属里。生成器自带一个随机源：

本地 MapGenerationRandomness.ktRNG 与 seedRNG · L14

RNG 是普通字段，默认 Random(42)；seedRNG 换成指定种子。generateMap 入口调过一次 seedRNG，此后所有阶段共用这同一个 Random 实例。

注意噪声的 seed 参数不是地图种子：它是“从这条噪声云里切哪一层”的 z 位置。各阶段在开工时先从 RNG 里抽一个数当本阶段的 z（例如湿度、温度各抽一次），所以整张地图的噪声场最终仍由地图种子唯一决定。

chooseSpreadOutLocations 也在这里：资源摆放“拉开距离选点”用它，同样从 RNG 取随机数。至此，阶段链上每一处随机都汇到同一个源头。

环绕地图还有一个特殊处理：普通 2D 噪声在左右边界有接缝，生成器把平面卷成圆柱来消除：

// MapGenerationRandomness.getNoise（环绕分支，部分代码）：
val worldCoords = HexMath.hex2WorldCoords(tile.position)
val params = tile.tileMap.mapParameters

// 不环绕的地图用标准 2D 噪声，边缘自然有接缝
if (!params.worldWrap)
    return noiseFunction(worldCoords.x.toDouble(), worldCoords.y.toDouble(), seed, …)

// 把 2D 平面卷成 3D 圆柱：左边缘(0°)与右边缘(360°)
// 在 3D 噪声空间占据同一坐标，过渡在数学上完美无缝
val radius = if (params.shape == MapShape.rectangular) {
    val width = params.mapSize.width
    val adjustedWidth = if (width % 2 != 0) width - 1 else width
    adjustedWidth / 2.0
} else params.mapSize.radius.toDouble()
val wrapPeriod = 3.0 * radius
val angle = (worldCoords.x / wrapPeriod) * 2 * PI
val cylinderRadius = wrapPeriod / (2 * PI)
// …offsets 由阶段 seed 算出（省略）…
val nx = cylinderRadius * cos(angle) + offsetX
val ny = cylinderRadius * sin(angle) + offsetY
val nz = worldCoords.y.toDouble() + offsetZ
return noiseFunction(nx, ny, nz, …)

不环绕时直接把地块的世界坐标喂给噪声，左右两端没有关联，会各长各的。第六课的环绕世界要求左右边界无缝衔接，地形也不例外——玩家走到最右再往右，看到的应该是连续的陆地，而不是一条颜色断层。

环绕时把水平坐标映射成圆柱表面的角度：x 平移一个 wrapPeriod 就走完一整圈，所以左边缘与右边缘落在 3D 噪声空间的同一个点上。竖直坐标直接当圆柱高度。噪声细节（倍频、振幅）是第 08 课的内容，这里只确认一点：三个 offset 也是由本阶段的 seed 算出的常数，仍在地图种子的控制范围内。

stateBasedRandom 用一个哈希造随机源：调用方名字、固定 seed 和整个 GameContext 的状态。哈希的第二项是 gameId——每局用 SecureRandom 生成的 UUID，所以不同的局，即使地图参数完全相同，这里造出的随机序列也不同。

GameStarter 的 rng 在构造时固定下来，用来选出生点、起始单位等开局设置。也就是说：地形跟着 seed 走，出生点跟着 gameId 走。

哈希里还有一个兜底：没有 gameInfo 时，这一项退到 mapParameters.seed——测试直接调 generateMap 不传 gameInfo，随机就回到种子上，测试因此稳定。

把可复现范围整理成三条：

  1. 同 seed 必同：generateMap 里所有用 randomness.RNG 的阶段——陆海、温湿、山脉、植被、冰、河流、编辑器资源铺放，以及镜像。地形整体可复现。
  2. 同 seed 不同：GameStarter 里用 stateBasedRandom 的开局设置——出生点等，它们随 gameId 每局不同。第 1 节的类注释说的正是这条边界。
  3. 小心两处例外：seed 为 0 时被换成当前毫秒（玩家没选种子）；编辑器分步生成每次从 seed 重置随机源，但重跑一步的结果还取决于地图当前状态，不一定与整图生成时一致。
取舍：为什么拆成两套随机

地图 seed 可复现，玩家才能分享“一张好图的种子”，编辑器也能稳定重跑阶段、开发者能复现 bug。开局设置跟着 gameId 走，同一张种子重开两局，地形一样而各家出生点不同——每局仍有新鲜感，也不让“记住种子”等价于“记住整局”。代价是：一张图对应多局时，出生点无法仅由种子重算。这正应了第 4 课的说法：测试不传 gameInfo，就是为了让断言落在种子可控的那一半上。

心智模型

  • MapGenerator 是无状态工具：实例只留规则集与协程作用域，输入输出全走 generateMap / generateSingleStep。
  • 三个入口共用一条链：新游戏传 gameInfo，编辑器与主菜单背景不传；传不传决定第 3 节的分支。
  • 阶段顺序即依赖：先陆海与温湿，再高程、湖岸、植被、冰，地形定稿后编号大洲、放河流、转换，最后收尾校正。
  • 新游戏分支跑区域与区域资源；编辑器分支直铺资源并多一步镜像；两者最后都过 TileNormalizer。
  • generateMap 入口 seedRNG(seed)：全部地形阶段共用同一个 Random，同 seed 同地形。
  • 出生点等开局设置走 stateBasedRandom，哈希混入 gameId：同 seed 重开，地形一样、出生点不同。
