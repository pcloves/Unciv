第一阶段 / 建立全局模型

怎样用证据读源码

前三课是“追着源码读”：按钮到下一回合、数据归谁、一条规则怎样进入游戏。这一课换一个入口——从测试读起。测试是项目里另一批一等公民源码，它既记录了“这段代码该怎么用”，也留下了“我改这里会破坏什么”的证据。学会读测试，就是把“我觉得对”换成“断言过了吗”。

需要的基础：前三课的运行链、三类数据和规则链，以及基础 Kotlin。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标、回顾与场景

先给一个场景：你怀疑卖建筑时黄金加得不对，想验证，又不想启动整个游戏去点半天。Unciv 的答案是把最小的一局游戏“摆”进内存，用一个测试跑一遍卖建筑，再断言黄金增加了 4。测试就是源码的“可执行说明书”——它替你准备好输入，告诉你预期，还指出关键断点在哪一行。

先找回前三课的一条主线

第一课追了按钮到新局面的调用链；第二课把数据分成状态、规则定义、运行时引用三类；第三课追了一条规则从 JSON 到产出加一的全程。这三课的共同点是顺着调用读。这一课反过来：从断言倒着读——测试先告诉你“结果必须是什么”，你再回到源码找“为什么是这个结果”。

本课的三个问题

  • 测试在哪：测试源码放在哪里，运行需要什么环境？
  • 断言说明什么：一条测试的输入、预期和关键断点分别是什么？
  • 怎么用起来：读档测试怎样用真实存档当证据，我又怎么在本地跑通？

读测试时记住这条主线：给定（given）→ 执行（when）→ 断言（then）。每一条断言都是一个“预期”：它失败，说明某段代码没有按预期走。

先认识四个概念

  • 测试运行器（Test Runner）：启动并运行测试的壳。Unciv 多数测试用 BaseTestRunner，直接在调用线程上跑，不启动游戏窗口；需要 GL 上下文的才用 GdxTestRunner。
  • TestGame：测试专用的一局最小游戏工厂，造规则集、地图、文明、城市和单位，全在内存里。
  • 断言（assert）：JUnit 里的检查语句，例如 assertEquals(4, civ.gold)；不满足就让测试失败。
  • 读档测试：拿一段真实历史存档字符串读回成 GameInfo，验证旧存档仍能还原。

1. 测试也是一等源码，入口和运行环境要先找对

2. 断言：把一条测试拆成输入、预期、关键断点

测试最典型的结构是 JUnit 的三段式，Unciv 里约定写成 given / when / then 注释。读任何一条测试，先问三个问题：输入是什么？预期是什么？失败时最先怀疑哪一行？用 CityTest 里“卖建筑”这条来做例子。

// tests/src/com/unciv/logic/city/CityTest.kt 的一条测试。
@Test
fun `should sell building`() {
    // given：给首都建一座纪念碑，预期卖出得 4 黄金
    val expectedMonumentSellingGoldGain = 4
    capitalCity.cityConstructions.addBuilding("Monument")

    // when：卖掉这座建筑
    capitalCity.sellBuilding("Monument")

    // then：文明国库恰好多了 4
    assertEquals(expectedMonumentSellingGoldGain, testCiv.gold)
}

输入是“一座已建成纪念碑的首都”；执行是调用 sellBuilding("Monument")；预期是 testCiv.gold == 4。这条测试没有启动游戏、没有点界面，只在内存里演了一遍。

测试替读者锁住了“卖建筑”这个动作的可见后果：国库增加卖价。读到这里你还不知道“为什么是 4”，但你已经知道“必须是 4”——这就是预期。下一步顺着它进生产代码找答案。

关键断点：预期值是怎么来的

现在答案浮出来：卖价 = 建筑成本的十分之一。测试里 4 这个魔法数，正是“纪念碑成本 / 10”的整数结果。如果哪天有人改了 cost / 10 成 cost / 5，这条测试立刻变红——这就是断言的回归保护作用。

关键断点是断言一旦失败、你最该先看的那一行：这里是 getGoldForSellingBuilding 的 cost / 10。读测试时把“预期”和“产生预期的那行生产代码”对上，才算是读懂了这条测试，而不是只认得 4 这个数字。

另一种断言写的是“关系”而不是“确定数值”。看人口课里的一条，它不猜增长后粮食到底剩多少，而是断言“有结转加成时剩得更多”：

// CityPopulationManagerTest 里的结转加成测试（部分）。
fun `should start with food stored when new pop is born and uniques`() {
    // given：给城市一座“增长后保留 50% 粮食”的建筑
    val building = testGame.createBuilding(
        "[50]% Food is carried over after population increases [in this city]")
    city.cityConstructions.addBuilding(building)
    city.population.foodStored = 14

    // when：这一回合净增 1 粮食，人口应增长
    city.population.nextTurn(1)

    // then：人口变 2，且结转后粮食剩 7
    assertEquals(2, city.population.population)
    assertEquals(7, city.population.foodStored)
}

本地 CityPopulationManagerTest.kt结转测试 · L168

这里用一个 createBuilding 现造一条规则字符串——正是第三课讲的 unique 模板（CarryOverFood），测试作者不用翻 JSON，直接写进建筑。nextTurn(1) 是模拟“本回合粮食净增 1”，人口从 1 涨到 2。

预期 7 是这样来的：涨人口前需要 14 粮食（人口 1 的标准门槛），14 加上净增的 1 后超过门槛，先扣掉 14 剩 0，再按 50% 结转回 7。这个“7”只有读了 CityPopulationManager.nextTurn 里 CarryOverFood 那段才能对上，它把一条规则的具体数值后果钉死在测试里。

设计取舍：确定性数值 vs 关系断言

像 4、7 这样的确定值，好处是任何算法改动都会被立刻抓出来，坏处是规则数值一调就要跟着改测试。像 assertTrue(a < b) 这样的关系断言更稳，但只能证明“方向对”，证明不了“多多少”。Unciv 两种都用：卖价、结转这类核心公式用确定值；难度对增长的影响用 assertTrue 比较大小。读测试时先分清它锁的是“值”还是“关系”，再决定改动后要不要同步更新这条测试。

3. TestGame：怎么造一局不启动游戏的对局

上面的测试开头都有 private val testGame = TestGame() 和 @Before fun setUp()。这就是 TestGame 的价值：它把“摆一个局面”压缩成几行。看它初始化时做了什么：

// TestGame 构造器里的初始化（部分代码）。
init {
    if (!forUITesting) {
        // 让 UncivGame.Current 就位，调试变量与设置可用
        UncivGame.Current = UncivGame()
        UncivGame.Current.settings = GameSettings().apply {
            musicVolume = 0f; soundEffectsVolume = 0f // 静音
        }
    }
    UncivGame.Current.gameInfo = gameInfo

    // 克隆一份可改的规则集，并设置 gameInfo 的关键变量

    ruleset = RulesetCache[BaseRuleset.Civ_V_GnK.fullName]!!.clone()
    gameInfo.ruleset = ruleset
    gameInfo.gameParameters.speed = Speed.DEFAULTFORSIMULATION
    gameInfo.setGlobalTransients()

    // 单格地图，城市中心需要它
    gameInfo.tileMap = TileMap(0, ruleset, false)
    tileMap.ruleset = ruleset
    tileMap.gameInfo = gameInfo

测试为什么能跑得又快又不碰界面

这些测试都标注 @RunWith(BaseTestRunner::class)。BaseTestRunner 的注释说得很直白：它“直接在调用线程上跑”，支持 Gdx.files，但不碰 Gdx.app、Gdx.input、Gdx.graphics——只有需要 GL 上下文或 Gdx 线程的测试才换 GdxTestRunner，后者用 mock 的 GL20 和 HeadlessApplication 模拟一个无头应用。这就是测试既不用打开游戏窗口、又能读真实 JSON 的原因：逻辑和界面被分开，测试只走逻辑那半边。BaseTestRunner.kt。

4. 读档测试：拿真实历史存档当证据

TestGame 造的是“我们想要的最小局面”，读档测试造的却是“玩家曾经真实存档的局面”。这类测试把一个压缩过的存档字符串读回成 GameInfo，验证旧存档到今天还能还原，是向后兼容的回归证据。先看读档的入口函数：

// core/.../files/UncivFiles.kt 中的读档入口（部分代码）。
fun gameInfoFromString(gameData: String): GameInfo {
    // 去掉换行回车，再尝试解压；解压失败就当作明文
    val fixedData = gameData.trim().replace("\r", "").replace("\n", "")
    val unzippedJson = try {
        FileConversions.unzip(fixedData)
    } catch (ex: Exception) { fixedData }

    val gameInfo = try {
        json().fromJson(GameInfo::class.java, unzippedJson)
    } catch (ex: Exception) {
        // 反序列化失败时，读出版本号，报版本不兼容
        throw IncompatibleGameInfoVersionException(...)
    } ?: throw UncivShowableException("The file data seems to be corrupted.")

    gameInfo.setTransients() // 补上运行时引用
    return gameInfo
}

本地 UncivFiles.ktgameInfoFromString · L429

读档的流程和第二课的结论完全对上：先反序列化成对象，再 setTransients() 把 @Transient 的引用（civ、centerTile、ruleset 等）按保存的 ID、名字、坐标补回来。存档里没有规则定义，只有规则集名字，所以 setTransients 里会按名字去 RulesetCache 取（第三课的 getComplexRuleset）。

读档失败分两种：解压/解析出错，或者版本号高于当前兼容版本——后者会抛 IncompatibleGameInfoVersionException。这正是读档测试要守护的边界：别让一个未来版本的存档悄悄读进来，再在别处崩溃。

类里存了几段真实存档的压缩字符串（H4sI... 是 gzip 的 base64 开头），注释标着每段存档的年代、规则集、玩家构成和推进到的回合。测试方法本身极短：就是把字符串交给 gameInfoFromString——只要不抛异常，就算读档成功。

这就是“证据”的用法：这些存档不是手写的理想输入，而是历史上某个版本真实生成的文件。每次升级序列化或规则后，只要这些旧档还能读回，就说明没破坏向后兼容。字符串太长被压缩存储，注释里那句“为去掉对向后兼容的依赖而更新”透露了维护方式——更新存档用第 4 节里 @Ignore 的工具测试。

// 三条被 @Ignore 的存档更新工具（部分代码）。
@Test
@Ignore("Use only to update the hardcoded value to remove reliance on backward compatibility")
@RedirectOutput(RedirectPolicy.Show)
fun updateVanillaGameString() {

    val newGame = oldGame.clone()
    val data = UncivFiles.gameInfoToString(newGame, forceZip = true, updateChecksum = true)

}

updateVanillaGameString · L56@Ignore 用法

带 @Ignore 的测试不会被正常跑（所以本机那次是 3 条“跳过”）。它们是维护用的：想更新某段存档时，临时去掉 @Ignore 跑一次，把控制台打印出的新字符串粘回 val，再把 @Ignore 加回来。这样“测试用的存档数据”和“被测试的读档逻辑”分开维护。

@RedirectOutput(RedirectPolicy.Show) 是 Unciv 自定义的注解，控制这条测试的标准输出直接打印（因为 println(data) 就是要给人看的）。普通测试默认 ShowOnFailure——平时吞掉输出，失败时才吐出来。这也解释了为什么测试跑起来很安静。

Godot 对照：先写最小场景，再写断言

同样的“用证据读源码”思路可以照搬到 Godot 4 C#：用一个不挂进场景树的纯 C# 类封装规则和状态，测试里构造最小输入、调用方法、断言结果，不依赖 _Ready 或渲染帧。Godot 4 自带 GdUnit 或自定义测试，也可以像 Unciv 这样把可复用的“最小对局工厂”抽成一个助手。关键是同一句纪律：先把“必须是 4”写下来，再去看代码为什么是 4。

心智模型

  • 测试是一等源码：它和主源码同包同目录，注释与类名本身就是“这段代码该怎么用”的说明。
  • 一条测试 = 输入（given）→ 执行（when）→ 预期（then）；断言失败说明某段生产代码没按预期走。
  • 关键断点是断言失败时最先怀疑的那一行；读测试要把“预期值”和“产生它的生产代码”对上。
  • TestGame 用克隆的规则集 + 单格地图 + 内存里的文明/城市，让你不启动游戏就能摆出任意局面；createBuilding 可以现造规则。
  • 测试进程的工作目录指向 android/assets，逻辑与界面被 BaseTestRunner 分开，测试只走逻辑那半边。
  • 读档测试拿真实历史存档当证据，验证旧档能读回、版本边界不被悄悄突破。

检索与推演

先不看上面的代码，凭记忆回答。选错了，再回到对应段落弄清原因。选择题只是热身；能选一条现有测试、写清输入预期与断点、并本地跑通，才说明这节课的主要内容已经理解了。

1. TestGame 的规则集为什么可以随意修改？
2. 单元测试里的断言主要证明什么？
3. 普通测试为什么不需要启动游戏窗口？
4. 读档测试为什么用整段存档字符串？
选择题答案与核对位置

1：它克隆了内置规则集的副本；2：输入经过执行得到预期结果；3：断言只依赖游戏逻辑的对象；4：用真实存档来验证还原能力。分别对应 测试入口、断言三要素、TestGame、读档测试。

练习 A · 选一条测试写三要素（5 分钟）

打开 CityTest.kt，选“卖建筑”之外任意一条测试，写出它的输入、预期和关键断点，并到生产代码里找到产生预期的那一行。

展开核对要点

以 should move capital when destroyed 为例：输入是两座城，其中一座叫 “Not capital”；执行是 capitalCity.destroyCity(overrideSafeties = true)；预期是毁掉的不是首都、且新首都成了 “Not capital”。关键断点在 City.destroyCity 里 if (isCapital()) civ.moveCapitalToNextLargest(null) 这一行——它保证首都先转移再移除。任何一条测试都能按这个模板拆。

练习 B · 预测卖价（3 分钟）

如果把 getGoldForSellingBuilding 里的 cost / 10 改成 cost / 5，第 2 节那条 should sell building 会发生什么？断言还能过吗？

展开答案

过不了。纪念碑成本不变，卖价变成成本 / 5，测试里预期的 4 就对不上 assertEquals，测试变红。这正是确定值断言的回归保护：算法一变，测试立刻报警。要改算法，就得连同测试里的预期值一起改，并确认新数值符合设计。

练习 C · 本地跑通核验（10 分钟）

在你的本地环境跑一条测试作为“可运行环境核验”：用 :tests:test --tests "com.unciv.logic.city.CityTest"（Gradle），或按 Building-Locally.md 的说明在 IDE 里跑 “Run unit tests”。记录结果：跑了几题、过几题、有无跳过。

展开核对要点

正常应看到 CityTest 的 14 个方法全过、0 失败（本题不含 @Ignore，所以不应有跳过）。若第一步就报资源或规则集错误，多半是工作目录没指向 android/assets——回看第 1 节的 workingDir。跑通后你就完成了一次“用证据核验理解”：绿条本身不是你写的证据，但它是环境就绪、源码与你手上版本一致的证据。

原文与下一次复习

建议先读：TestGame.kt 的类注释和构造器，再挑一条你关心的测试，比如 CityTest.kt，把它和生产代码对照读一遍。想理解无头运行再看 BaseTestRunner.kt 的类注释，最后在 LoadGameTest.kt 里体会“真实存档当证据”。下一课进入地图专题，会用到 HexmathTests.kt——那时你已经会读测试了。

下次学习前，用两分钟复述“given / when / then / 关键断点”四要素；约一周后再做练习 B。如果只记得断言写法却说不出它钉住了哪行生产代码，翻一下测试与证据速查，弄清卡住的地方后合上资料再试一次。
