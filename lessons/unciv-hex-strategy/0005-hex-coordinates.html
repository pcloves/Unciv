第二阶段 / 地图专题

六边形如何编号

地图专题的第一课，回答一个最基础的问题：一块六边形地块，代码用什么数表示它在哪？Unciv 的答案是两个整数（x, y），配上一套“怎么找邻居、怎么算距离、怎么换成屏幕像素”的换算。这套编号是整个地图系统的地基——生成、寻路、显示、存档全都站在它上面。

需要的基础：第二课的数据归属（坐标存哪里、存档怎么序列化）、第四课的 given/when/then 读测试法。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标、回顾与场景

先给一个场景：你在做一个六边形策略游戏的地图编辑器，点击屏幕上的某个位置，要把它变成画笔目标——也就是说，把“屏幕上的一个点”变回“某一块地块”。反过来，画大地图时你想知道两个出生点隔了几格，决定玩家开局会不会立刻接壤。这两个需求在 Unciv 里都由一个文件解决：core/src/com/unciv/logic/map/HexMath.kt，里面有坐标类型 HexCoord 和一套纯函数 HexMath。

先找回第四课的读法

第四课学了从断言倒着读源码：给定（given）→ 执行（when）→ 断言（then），再把“预期值”和“产生它的生产代码”对上。本课就直接练手：tests/src/com/unciv/logic/map/HexmathTests.kt 里 8 条测试，全是关于编号、距离和存档格式的断言——读懂了它，你就知道这套坐标在作者眼里“必须长什么样”。

本课的四个问题

  • 两个数怎么指位置：x 和 y 各指向哪个方向，为什么这么选？
  • 邻居怎么算：六个邻居对应的坐标偏移是什么，代码里由谁维护？
  • 距离怎么算：getDistance 的两分支公式为什么对？
  • 约定差在哪：这套编号和 Red Blob 教程里的轴向坐标有什么不同，移植公式要注意什么？

读完还要会一件事：不看资料，手算任意一块地的邻居和两点距离。

先认识三个概念

  • 轴向坐标（Axial）：只用两个整数表示六边形网格上的位置，例如 (x, y)。Unciv 的 HexCoord 就是轴向坐标。
  • 立方坐标（Cube）：用三个数 (a, b, c) 表示同一个位置，且 a+b+c 恒为 0。很多公式在立方坐标里最简洁，Unciv 在“取整”时也会临时用它。
  • 时钟方向（Clock Position）：用 12、2、4、6、8、10 点钟指六个邻居方向，例如 10 点钟就是左上。

1. 两条斜轴：x 与 y 各指向哪里

先看坐标类型本身。它没有“东西南北”这类枚举，就是两个整数，配上加减乘等不可变运算：

轴方向注释 · L101

x 轴指向左上的邻居（10 点钟），y 轴指向右上的邻居（2 点钟）。两条正向轴在画面上夹 120°；原教材写成 60° 有误。Unciv 的六边形是平顶摆放，正上、正下各有一个邻居，其余四个在斜向。

x、y 各加 1，左右分量抵消、向上分量相加，就到了正上方邻居 (1,1)。反方向 (−1,−1) 向下。原英文注释末尾将 (−1,−2) 描述为“右下邻居的下方”，与实际偏移表不符：(0,−1) 是左下邻居，再向下得到 (−1,−2)；右下邻居 (−1,0) 再向下应为 (−2,−1)。这里以偏移表和 hex2WorldCoords 为准。

以 (0,0) 为中心，这六个邻居在屏幕上的样子：

                (1,1)       ← 12 点钟：正上方
          (1,0)      (0,1)  ← 10 点钟（x 轴）/ 2 点钟（y 轴）
                (0,0)       ← 自己
          (0,-1)     (-1,0) ← 8 点钟 / 4 点钟
                (-1,-1)     ← 6 点钟：正下方

下面选几行地块，按画面从左到右排列。每一行都有相同的 x+y：

  x+y= 2    (2,0)      (1,1)      (0,2)
  x+y= 1        (1,0)      (0,1)
  x+y= 0   (1,-1)      (0,0)      (-1,1)
  x+y=-1        (0,-1)     (-1,0)
  x+y=-2   (0,-2)     (-1,-1)     (-2,0)

x+y 相同的地块中心排在一条水平线上，y−x 相同的地块中心排在一条竖直线上。源码的命名需要分清：getLatitude = x+y，getLongitude = x−y，getColumn = y−x。经度与列号互为相反数，都描述左右位置，正方向相反；原教材将 y−x 写成 getLongitude 有误。

可以先把 x+y 当作高度量、y−x 当作向右增大的列号。x、y 本身是两个斜轴坐标，不能把 x 当作屏幕横轴。第六课从两条斜轴的水平、竖直分量推导这两组和差。

2. 六个邻居：一张偏移量表

邻居不是用一堆 if 写出来的，而是集中放在一张表里：几点钟方向的邻居对应哪个坐标偏移。先看这张表和配套的方向枚举：

表里 0 点钟和 12 点钟映射到同一个偏移 (1,1)，注释说这是为了让“对 12 取模”的钟点运算更简单：代码里按小时数循环方向时，拿到 0 和 12 都能命中正上方。

把表和第 1 节的图对照：12 点钟（正上）是 (1,1)，2 点钟（右上）是 (0,1)——只加 y 轴，10 点钟（左上）是 (1,0)——只加 x 轴。剩下的 4、6、8 点钟就是这三个偏移取负。六边形邻居的几何事实，落到坐标上就是这六个固定偏移。

取邻居的代码就在 TileMap 里，逻辑只有两步——坐标加偏移，再查地图：

3. 距离：两分支公式背后的立方坐标

六边形的“格数距离”不是欧氏距离，而是最少跨几条边。看 getDistance 的实现，主体就一个两分支判断：

// HexMath.kt：不带环绕的六边形距离（三个重载，核心是这个）。
@Pure
fun getDistance(originX: Int, originY: Int,
                destinationX: Int, destinationY: Int): Int {
    val relativeX = originX - destinationX
    val relativeY = originY - destinationY
    return if (relativeX * relativeY >= 0)
        max(abs(relativeX), abs(relativeY))
    else
        (abs(relativeX) + abs(relativeY))
}

getDistance · L267

先算两个坐标差：relativeX、relativeY 分别是两格在 x 轴、y 轴上的差。同号（都非负或都非正）取两个绝对值中大的那个；异号取两个绝对值之和。为什么这样分？光看这四行很难直接想通——这正是“先读注释再读代码”没有覆盖的部分，注释里没有解释，需要借用仓库里的另一段代码。

答案在 roundHexCoords 内部的局部函数里：Unciv 自己写了六边形坐标 ↔ 立方坐标的换算。把 x、y 想象成三个立方分量中的两个，第三个由“三者之和为 0”补出来，距离公式就一目了然。

// roundHexCoords 里的局部函数（HexMath.kt，部分代码）。
// 六边形坐标 → 立方坐标：第三个分量 = 前两个的负和。
@Readonly
fun hex2CubicCoords(hexCoord: Vector2): Vector3 {
    return Vector3(hexCoord.y - hexCoord.x, hexCoord.x, -hexCoord.y)
}

// 立方坐标 → 六边形坐标：取第 2、3 个分量的相反数。
@Readonly
fun cubic2HexCoords(cubicCoord: Vector3): Vector2 {
    return Vector2(cubicCoord.y, -cubicCoord.z)
}

hex2CubicCoords · L200

立方坐标用三个数 (c1, c2, c3) 表示同一格，三个数之和恒为 0。Unciv 的取法是 (y−x, x, −y)：前两个就是熟悉的 y−x 和 x，第三个 −y 由和为零自动确定。

立方坐标的格数距离有个标准公式：三个分量各自的差取绝对值，再取最大。max(|Δc1|, |Δc2|, |Δc3|)。把 c1 = y−x、c2 = x、c3 = −y 代进去：Δc2 是 Δx，Δc3 是 −Δy，Δc1 是 Δy − Δx。于是距离 = max(|Δx|, |Δy|, |Δy − Δx|)——getDistance 的两分支，正是这个 max 的化简。

化简分两种情况。Δx、Δy 同号时，|Δy − Δx| 是“两个数的差”，不可能超过其中较大的那个，于是 max(|Δx|, |Δy|, |Δy−Δx|) = max(|Δx|, |Δy|)；异号时，|Δy − Δx| 变成“两个数的和”，一定最大，于是结果就是 |Δx| + |Δy|。代码里的两分支和立方公式是同一个数。

手算两个例子：从 (2,3) 到 (5,0)，Δx = −3、Δy = +3，异号 → 距离 6；从 (2,3) 到 (4,4)，Δx = −2、Δy = −1，同号 → 距离 2。想验证，把第 1 节的平面图摊开数边数，两个答案都数得出来。

设计取舍：为什么写两分支，不直接写立方公式

两分支版本没有中间变量，最快；但它把“为什么对”藏了起来，所以作者在 roundHexCoords 的注释里留下了 Todo: find a mathematically equivalent way to round hex coords without cubic magic——立方坐标是“数学上直白”的工具，Unciv 只在需要取整这种难直接化简的地方用它，热路径（距离）则手写化简版。读源码时遇到这种“看不懂但很快”的代码，先去找它附近的立方/几何注释或测试，通常就能还原出意图。

4. 像素与世界坐标：编号怎样变成屏幕位置

逻辑坐标定好了，还要回答开头场景里的问题：这块地画在屏幕哪里？反过来，点击的像素属于哪块地？两个函数正好一正一反：

// HexMath.kt：六边形坐标 → 世界坐标。
// 两轴取 10 点钟、2 点钟方向，各乘自己的坐标值，再放大 √3。
@Pure
fun hex2WorldCoords(hexCoord: HexCoord): Vector2 {
    val xVector = getVectorByClockHour(10)
    xVector.scl(sqrt(3.0).toFloat() * hexCoord.x)
    val yVector = getVectorByClockHour(2)
    yVector.scl(sqrt(3.0).toFloat() * hexCoord.y)
    return xVector.add(yVector)
}

// 钟点 → 方向向量：10 点钟 = 150°、2 点钟 = 30°。
@Pure
private fun getVectorByClockHour(hour: Int): Vector2 {
    return getVectorForAngle((2 * Math.PI * (hour / 12f)).toFloat())
}

hex2WorldCoords · L127

世界坐标 = √3 ×（x 倍的 10 点钟方向向量 + y 倍的 2 点钟方向向量）。展开为 worldX = 1.5·(y−x)，worldY = (√3/2)·(x+y)，其中 √3/2 约为 0.866。这是相邻中心距为 √3 的世界坐标；调用处再乘显示尺寸，例如 TileGroupMap 的 0.8 × groupSize。

y−x 是向右增大的列号 getColumn，x+y 是向上增大的纬度 getLatitude。源码经度 getLongitude = x−y 则向左增大，因此也可以写成 worldX = −1.5 × longitude、worldY = (√3/2) × latitude。核对见 经纬度函数 · L51 和 getColumn · L156。

反向换算（点击 → 地块）是解一个 2×2 方程组，解出来的坐标通常是小数，还要舍入到最近的六边形：

// HexMath.kt：世界坐标 → 六边形坐标（解方程组，结果可能是小数）。
@Readonly
fun world2HexCoords(worldCoord: Vector2): Vector2 {
    val D = getVectorByClockHour(10); D.scl(sqrt(3.0).toFloat())
    val A = getVectorByClockHour(2);  A.scl(sqrt(3.0).toFloat())
    val den = D.x * A.y - D.y * A.x
    val x = (worldCoord.x * A.y - worldCoord.y * A.x) / den
    val y = (worldCoord.y * D.x - worldCoord.x * D.y) / den
    return Vector2(x, y)
}

            Assert.assertFalse("Duplicate coords found: $coord", seenCoordsMapping.contains(mapping))
            Assert.assertTrue("Coords $coord should be in ring $ring, actual mapping $mapping",
                mapping in ringStartCoordinate .. (ringStartCoordinate + 6 * ring - 1))
            seenCoordsMapping.add(mapping)
        }
    }
}

第一条的 given 是“中心格 (0,0)”，断言它的连续编号是 0。第二条把整个坐标系扫了一遍：given 是第 1～100 环的全部坐标；then 有两个断言——编号落在本环的号段 [ringStart, ringStart + 6·ring − 1] 内，且与已见过的编号都不重复（否则报 “Duplicate coords found”）。

1 + 6·ring·(ring−1)/2 是环起点的公式：第 0 环只有 1 格，第 1 环有 6 格，第 2 环 12 格……累加后就是它。同文件里的 getNumberOfTilesInHexagon(size) = 1 + 6·size·(size+1)/2 是同一串数——六边形地图按“环”数格子，第 1 环编号 1～6，第 2 环 7～18，依次类推。

// HexMath.kt：连续编号的“教学版”实现（部分代码）。
// 逻辑等价、通过同样的测试，但慢约 5 倍。
fun mapRelativePositionToPositiveIntRedblob(x: Int, y: Int): Int {
    if (x == 0 && y == 0) return 0
    val ring = getDistance(0, 0, x, y)
    val ringStart = 1 + 6 * ring * (ring - 1) / 2
    val vectorsInRing = getHexCoordsAtDistance(HexCoord.Zero, ring, ring, false)
    val positionInRing = vectorsInRing.indexOf(HexCoord.of(x, y))
    return ringStart + positionInRing
}

教学版实现 · L363

连续编号 = 环起点 + 环内序号。环号用第 3 节的距离求，环内序号 = 自己在“环坐标列表”里的下标；这个列表由 getHexCoordsAtDistance 生成——它沿钟面走三条边、用“原点两倍减自己”镜像出对面三个方向（细节留给第 11 课的寻路与范围）。

生产用的 getZeroBasedIndex 不走这个列表，而是用一个 when 分支直接推环内序号（省下遍历，注释说快约 5 倍），测试保证两者同一。这份“简单版 + 快速版 + 同测试”的布局值得模仿：先用笨办法把语义写明白，再优化。

存档格式也钉在测试里。第二课讲过序列化：存档只写 ID、坐标、数值。坐标这块有三条测试：

6. 与 Red Blob 教程的约定差异

六边形算法的经典资料是 Red Blob Games 的《Hexagonal Grids》交互教程（课程 RESOURCES.md 已收录）。它和 Unciv 用的是同一套数学，但坐标轴的选取不一样。差异不在“谁对谁错”，而在屏幕方向和轴的选择，照抄公式会得到镜像或旋转过的结果。

方面Unciv 的约定Red Blob 轴向坐标的约定
六边形摆放平顶：正上、正下各有一个邻居教程按需介绍平顶/尖顶，公式各自成系
屏幕 y 轴向上（libGDX 场景坐标）示意图里 y 轴向下
坐标轴两条斜轴：10 点钟（左上）与 2 点钟（右上），没有水平轴轴向 (q, r)：一条水平轴加一条斜轴
“正上方”一步(1, 1)依变体不同，通常没有“正上方”一步
距离公式max(|Δx|, |Δy|, |Δ(y−x)|) 的两分支写法max(|Δq|, |Δr|, |Δq+Δr|)，同一个立方公式

两条距离公式是同一个数：它们都是立方坐标里 max(|Δc1|, |Δc2|, |Δc3|) 的改写，只是轴不同、变量名不同。Unciv 丢掉了水平轴、保留两条斜轴，因为它的屏幕布局正是按两条斜轴展开的（第 4 节：screenX ∝ y−x、screenY ∝ x+y）；Red Blob 保留水平轴是为了教学直观。

移植 Red Blob 算法时的核对顺序

  1. 先对齐邻居：把对方的邻居偏移表画出来，和本课的六偏移表对照，必要时旋转/镜像；
  2. 再核对距离：用第 3 节的手算例（(2,3)→(5,0) 得 6）验证公式是否等价；
  3. 最后移植其余：范围、寻路、旋转等公式都在“邻居+距离”正确的前提下才有意义；
  4. 以仓库为准：Unciv 的立方换算在 hex2CubicCoords（(y−x, x, −y)），有疑问时它和 HexmathTests 是最终依据。

为什么这种差异很常见

六边形坐标有轴向、立方、偏移三大族，乘上尖顶/平顶、屏幕 y 方向，能组合出十几种“看似相同”的约定。每套约定的公式都自洽，但跨约定搬运时必须显式转换——不能靠把 q 改名成 x、r 改名成 y 来“适配”。

Unciv 用两条斜轴表示地块，纬度取 x+y、经度取 x−y、列号取 y−x。读其他六边形代码时，也要先确定格子摆放方式、画面坐标正方向、保留的两条坐标轴，以及第三个立方分量的计算方法。

Godot 对照：画得出格子，但逻辑还得自己写

Godot 4 的 TileSet 自带六边形 tile_shape 和偏移轴设置，能直接画出六边形网格，world_to_map 也替你把像素换回格子坐标——对应本课的 hex2WorldCoords / world2HexCoords。但“哪一格是邻居”“两格隔几格”这类逻辑 Godot 不提供，正是 HexMath 干的活。照搬 Unciv 的分层即可：逻辑层用你选的轴向坐标 + 一张邻居偏移表（C# 里 Vector2I 当 Dictionary 键最顺手），渲染层交给 TileMapLayer。坐标约定只要和本课一样自洽并有测试钉住，用哪种轴都可以。

心智模型

  • 一块地 = 一对整数 (x, y)：x 指左上（10 点钟）、y 指右上（2 点钟），屏幕 y 向上，正上方邻居是 (1,1)。
  • 相邻 = 坐标加偏移；六个邻居的偏移是 ±(1,0)、±(0,1)、(1,1)、(−1,−1)，集中在一张钟点表里。
  • 距离不看直线：同号取 max、异号相加——它是立方坐标距离 max(|Δx|, |Δy|, |Δ(y−x)|) 的化简。
  • 世界坐标 worldX = 1.5(y−x)、worldY = (√3/2)(x+y)：列号 y−x 向右增大、纬度 x+y 向上增大；源码经度 x−y 与列号符号相反。
  • 点击反查 = world2HexCoords 解方程 + roundHexCoords 立方舍入 + 查地块，无需遍历。
  • HexmathTests 覆盖编号与坐标存档格式等行为；引用某条测试时，需看它具体断言了什么。
  • 不同轴向坐标约定之间要显式转换，不能换变量名照抄公式。

展开核对要点
