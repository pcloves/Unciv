第一阶段 / 建立全局模型

一条规则怎样进入游戏

第二课把规则定义归为“不写进存档”的一类数据。这一课把这句话打开：规则写在哪些文件里，什么时候读进内存，建成一座建筑时怎么进入这局游戏，最后又是哪个代码点让它真正改变一块地的产出。

需要的基础：Java 对象、集合、引用，以及基础 Kotlin；第二课的“三类数据”与 setTransients。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标、回顾与场景

先给一个具体场景：城市建成粮仓（Granary）后，城市里有人工作的鹿资源地块，每块多 1 食物。这条效果从哪里来？什么时候生效？为什么拆掉粮仓它就消失？整条链路上没有任何一个类在“执行”这条规则——效果是查询时套出来的。读懂这条链路，就理解了 Unciv 数据驱动的核心。

本课的三个问题

  • 定义放哪里：规则以什么形式存放？启动时谁把它们读进内存？
  • 怎样进对局：静态定义什么时候变成这一局里可以查询的东西？
  • 怎样生效：哪段代码在查询规则？条件、参数和倍率在哪里判定？

读源码时记住这条主线：JSON 定义 → 规则集缓存 → 本局规则集 → 进入对局对象的 uniqueMap → 使用点查询。每一站都问：这里的东西是静态共享的，还是这一局独有的？

先认识四个概念

  • 规则集（Ruleset）：一整套规则定义的集合，包含地形、建筑、单位、科技等；可以指内置规则集、模组或二者组合。
  • 规则（Unique）：一条可查询的效果或条件，在 JSON 里是一段带占位符的字符串，例如 [+1 Food] from [Deer] tiles [in this city]。
  • 占位文本（placeholderText）：把一条规则里的参数都压成 [] 后剩下的“模板”，用来查它属于哪种规则类型。
  • 判定场景（GameContext）：查询规则时带上的上下文（城市、地块、文明等），条件修饰语靠它判定。

1. 规则写在 JSON 里，启动时一次性加载

游戏包里有 android/assets/jsons/ 目录，内置两个规则集子目录：Civ V - Vanilla 和 Civ V - Gods & Kings，每个目录下是 Buildings.json、Units.json、Terrains.json 等文件。粮仓的定义在 Buildings.json 里：

// android/assets/jsons/Civ V - Vanilla/Buildings.json 中粮仓的定义。
{
    "name": "Granary",
    "food": 2,
    "maintenance": 1,
    "hurryCostModifier": 25,
    "uniques": ["[+1 Food] from [Deer] tiles [in this city]",
        "[+1 Food] from [Bananas] tiles [in this city]",
        "[+1 Food] from [Wheat] tiles [in this city]"],
    "requiredTech": "Pottery"
}

本地 Buildings.json · 粮仓定义本地 GlobalUniques.json

一条建筑定义由普通字段加 uniques 数组组成。food: 2 等数值直接给城市产出；uniques 里的字符串则每条都是一条带条件的规则。JSON 只是文本：谁把它读进内存、变成 Kotlin 对象？

答案在 Ruleset.load。规则集类的字段与文件名一一对应，这个对应关系由 RulesetFile 枚举声明：

// Ruleset.load 的部分代码：按文件名读 JSON 并填进对应字段。
fun load(folderHandle: FileHandle) {
    fun RulesetFile.file() = folderHandle.child(filename)

    val buildingsFile = RulesetFile.Buildings.file()
    if (buildingsFile.exists()) buildings += createHashmap(
        json().fromJsonFile(Array<Building>::class.java, buildingsFile))

    val unitsFile = RulesetFile.Units.file()
    if (unitsFile.exists()) units += createHashmap(
        json().fromJsonFile(Array<BaseUnit>::class.java, unitsFile))
    // ...其余文件类似：逐个存在则读，不存在就跳过
}

// createHashmap：按 name 建表，顺便记下对象来自哪个规则集。
private inline fun <reified T : INamed> createHashmap(items: Array<T>): LinkedHashMap<String, T> {
    val hashMap = LinkedHashMap<String, T>(items.size)
    for (item in items) {
        val itemName = try { item.name }
        catch (_: Exception) { throw Exception("${T::class.simpleName} is missing a name!") }
        hashMap[itemName] = item
        (item as? IRulesetObject)?.originRuleset = name
    }
    return hashMap
}

Ruleset.load · L369、L399createHashmap · L205

读出的是 Array<Building> 这样的对象数组，libGDX 的 JSON 库按字段名把 JSON 填进对象。数组里的每个建筑按 name 存进 LinkedHashMap，之后代码用 ruleset.buildings["Granary"] 按名字取。

originRuleset 记下定义来源，供翻译、报错和模组覆盖时使用。为什么用 LinkedHashMap 而不是 HashMap？源码注释强调过顺序：定义文件里的先后（比如时代顺序）不能丢，普通 HashMap 不保证遍历顺序。

还有两类特殊处理：科技带层级，先读列再展开成 technologies 表；内置规则集缺省的文件（如没有 Ruins.json）会从 Vanilla 里补一份兜底，保证游戏始终有完整定义。

启动时由 RulesetCache 加载并缓存

// RulesetCache.loadRulesets 的部分代码。
// 加载模组很贵，所以只在启动时做一次，把结果存进缓存。
object RulesetCache : HashMap<String, Ruleset>() {
    fun loadRulesets(consoleMode: Boolean = false, noMods: Boolean = false): List<String> {
        val newRulesets = ConcurrentHashMap<String, Ruleset>()
        fun getBuiltinRulesetFileHandle(ruleset: BaseRuleset): FileHandle {
            val fileName = "jsons/${ruleset.fullName}"
            return if (consoleMode) FileHandle(fileName)
            else Gdx.files.internal(fileName)
        }
        fun loadBuiltinRuleset(ruleset: BaseRuleset) {
            val fileHandle = getBuiltinRulesetFileHandle(ruleset)
            newRulesets[ruleset.fullName] = Ruleset().apply {
                name = ruleset.fullName
                load(fileHandle)
            }
        }
        // 两个内置规则集并行加载；必须先就位，
        // 模组缺省的部分才能从它们兜底补齐。
        Concurrency.parallelize(builtinRulesetTasks, parallel)
        this.putAll(newRulesets)
        // ...再并行加载 mods 目录下的每个模组
    }
}

排查思路：定义改了对局没反应？

先分清改的是哪一份：android/assets/jsons/ 是内置定义，游戏打包时固定；mods/ 目录才是玩家模组。改了内置 JSON 后，旧缓存不会自己刷新——loadRulesets 只在启动时跑一次，模组界面改模组时才重新加载。规则集按名字缓存这一设计，正是第二课“读档只存规则集名字”能成立的前提。

2. 每局游戏组合出自己的规则集

缓存的规则集是“全部可选规则”的静态定义。开局或读档时，GameInfo.setTransients 按这局的设置（基础规则集 + 启用的模组）组合出一份属于这一局的规则集。第二课已经见过这一行：

// GameInfo.setTransients 的部分代码：按开局设置组合本局的规则集。
ruleset = RulesetCache.getComplexRuleset(gameParameters)

// 存档里提到的模组没有安装时，直接报错而不是默默少一套规则。
val missingMods = (listOf(gameParameters.baseRuleset) + gameParameters.mods)
    .filterNot { it in ruleset.mods }
if (missingMods.isNotEmpty())
    throw MissingModsException(missingMods)

// 把本局规则集指回定义对象，供它们查询同规则集里的其他对象。
for (baseUnit in ruleset.units.values)
    baseUnit.setRuleset(ruleset)
for (building in ruleset.buildings.values)
    building.ruleset = ruleset

本地 GameInfo.ktgetComplexRuleset · L736缺模组检查 · L741回指规则集 · L749、L752

gameParameters 是写进存档的开局设置，里面有基础规则集名字和模组列表。所以读档后，只要规则集名字还在、缓存里还查得到，就能组合出和当初一致的定义——这正是规则定义不必写进存档的原因。

缺模组时抛 MissingModsException：宁可拒绝读档，也不让游戏带着残缺的规则集运行，因为后续代码会按名字查建筑、单位，查不到就是空指针或静默错误。

building.ruleset = ruleset 值得注意：定义对象身上有指向“当前这局规则集”的可变引用。如果两局同时存在、或者模组直接改了缓存里的对象，这个回指就会混乱。Unciv 一次只处理一局游戏，所以没问题，但读源码时要意识到定义对象并非完全不可变。

组合出的 newRuleset 是一个全新的容器：它的 buildings、units 等 Map 都是新的，先并入模组内容，基础规则集最后放入，同名定义被模组覆盖。建筑费用不能在每个文件读完后立刻算，因为模组可能改科技列；所以放到全部加入之后统一算。

细看 putAll：放进新 Map 的是同一个 Building 对象的引用。也就是说，缓存的静态定义对象和每局规则集里的定义对象是同一批实例，只有“容器”（Map 本身）每局一份。这样几千个定义对象不用每局复制一遍；代价是任何一处修改都会影响其他引用者，所以约定“定义对象只读”。getVanillaRuleset 每次都 clone 新容器再交出去，就是这个约定的保险。

设计取舍：静态定义共享，实例容器隔离

如果每局复制全部定义对象，开局和读档都会变慢，内存也翻倍。Unciv 的选择是：定义对象共享、每局只建新容器。这带来一条纪律：不要修改定义对象本身；要“改规则”只能换一份定义（模组覆盖同名对象），或把运行时状态写在别处。上一课 City.tiles 存坐标不存对象，是同一个思路：数据只有一份，容器和引用分开。Godot 里多场景共享同一份自定义 Resource 时规则相同：改模板影响所有引用者，实例数据要放在各自对象里。Godot 官方 Resource 说明。

3. 一行 unique 从字符串变成对象

JSON 里的 uniques 是字符串数组。Unciv 没有在加载时把每一条都解析成对象，而是第一次被访问时才解析。先看解析逻辑，再看惰性藏在哪里。

本地 Unique.ktUnique · L19、L22StatsFromTiles · L50uniqueTypeMap · L1210

左侧第一段是解析核心。getPlaceholderText 先把尖括号修饰语摘掉，再把每个 [...] 里的参数替换成 []，剩下只含方括号骨架的“模板”；getPlaceholderParameters 按顺序取出参数。粮仓那条规则的模板和参数，就写在字段上方的注释里。

模板是查找键：左侧第二段声明 StatsFromTiles 枚举项时，自带的文本正是模板本身；第三段在启动时把全部枚举项建成 uniqueTypeMap 对照表。于是 type = uniqueTypeMap[placeholderText] 这一行查表，粮仓的模板 "[stats] from [tileFilter] tiles [cityFilter]" 命中 StatsFromTiles，这条字符串就有了类型；参数 "+1 Food"、"Deer"、"in this city" 留给使用点取数，第 5 节会看到它们各自做了什么。UniqueType 枚举有 600 多个条目，每条声明了自己的模板和可挂载的目标。

最后一行 modifiers 单独处理尖括号里的条件修饰语，带条件的规则看下面的例子。

带条件的规则把条件放进尖括号，主句和修饰语各自解析成 Unique：

解析为什么是惰性的

// RulesetObject 中唯一对象的惰性解析（部分代码）。
abstract class RulesetObject : IRulesetObject {
    // JSON 里的原始字符串；定义对象之间的覆盖也改这个列表。
    override var uniques = ArrayList<String>()

    // 第一次访问时把字符串解析成 Unique 对象，之后复用。
    @delegate:Transient
    override val uniqueObjects: List<Unique> by lazy(::uniqueObjectsProvider)
    @delegate:Transient
    override val uniqueMap: UniqueMap by lazy(::uniqueMapProvider)
}

// IHasUniques 中的解析实现（部分代码）。
fun uniqueObjectsProvider(uniques: List<String>): List<Unique> {
    if (uniques.isEmpty()) return emptyList()
    return uniques.map { Unique(it, getUniqueTarget(), name) }
}

本地 RulesetObject.kt · L14本地 IHasUniques.ktuniqueObjectsProvider · L32

启动时载入了几千个定义对象，多数规则的唯一对象只在被查询（城市建成建筑、界面显示描述）时才会用到。惰性解析让没被用到的字符串保持原样，不产生对象；正则解析还很贵，解析一次后用 lazy 缓存住。

@delegate:Transient 作用在 lazy 委托上：存档序列化时跳过这个计算属性，反序列化时它仍处于“未解析”状态，下次访问才解析。这和第二课“缓存要在读档后重建”是同一套机制，只是这里的缓存能安全地自己懒加载。

解析结果按类型分组放进 UniqueMap，查询时不需要遍历全部规则，直接按类型取列表。分组时同一条 Unique 对象同时进两个表：按类型查的表和按模板查的表，两份表共享同一批列表对象以省内存。类型解析失败的（拼写错、已废弃）进不了类型表，只有规则校验器会报告它。

设计取舍：数据驱动 vs 硬编码

把“粮仓给鹿地块加 1 食物”写进 JSON 而不是写死在代码里，模组作者不用改 Kotlin 就能加新建筑、改数值、覆盖官方定义。代价是字符串解析、按类型分组的查找表、拼写错误要到校验时才暴露。若规则数量很少、改动不频繁，硬编码枚举反而简单；Unciv 有 600 多种规则类型、要支持大量模组，数据驱动才划算。注意数据驱动不等于“玩家随意改”：规则文本有严格的模板语法，参数类型也由 UniqueParameterType 声明，校验器逐条对照检查。

4. 规则进入对局：建成建筑的那一刻

定义对象一直在缓存里，但一条规则要影响游戏，必须先进入这局的状态。对建筑来说，关键时刻是建成和拆除：城市把已建建筑的 Unique 对象收集进自己的一个 Map。

本地 UniqueMap.ktgetMatchingUniques · L81conditionalsApply · L89

三层来源只是初筛，取到的每条规则还要过两道关。

第一道是条件：conditionalsApply 拿上下文判定 <when ...> 修饰语。比如快乐度不在 -10 到 -1 之间，第 3 节那条“-75% 增长”就被跳过。条件不满足时静默返回空，是“规则在但没效果”的常见原因。

第二道是倍率：getMultiplied 按 <for every ...> 之类修饰语把一条规则展开成多条。

两道关用的上下文都装在 GameContext 里：城市、地块、文明、单位等对象，以及“忽略条件”之类的开关。查询方构造它，被查询的规则拿它回答“现在满足吗”。

排查思路：规则没生效，分三层问

① 定义里有没有这条规则？去 JSON 和 uniqueObjects 看字符串，注意模板必须与 UniqueType 的写法完全一致；② 规则有没有进入这局？建筑建成了吗、它的 Unique 在 builtBuildingUniqueMap 里吗；③ 使用点有没有查这个类型、条件是否满足？条件不满足时 getMatchingUniques 会静默返回空，表现就是“规则在但没效果”。按定义、进入、查询的顺序查，比盯着使用点乱猜快得多。

5. 使用点：一块地的产出怎样加上 1 食物

最后一站：哪段代码在“执行”粮仓的效果？答案是城市重算产出时，对每块有人工作的地逐条套规则。分三步看：先看遍历了哪些地块，再看查出了什么规则，最后看规则怎样套到当前地块上。

第一步：只统计有人工作的地块

// CityStats.updateTileStats 的部分代码。
// 过滤条件里还有城市中心、免人口的地块改良，这里省略。
fun updateTileStats() = timeThis("updateTileStats") {
    val stats = Stats()
    val workedTiles = city.tilesInRange.asSequence()
        .filter { city.location.toHexCoord() == it.position
            || city.isWorked(it) || ... }
    for (tile in workedTiles) {
        val tileStats = tile.stats.getTileStats(city, city.civ)
        stats.add(tileStats)
    }
    statsFromTiles = stats
}

本地 CityStats.ktupdateTileStats · L349、L365

重算城市产出时，先筛出有人工作的地块，然后对每一块调用 getTileStats(city, city.civ)，把算出的产出累计进 statsFromTiles。

这就是粮仓效果范围的答案：粮仓不加给城市里所有鹿地块，只加给走进这个循环的地块。有鹿但没人工作的地块不参与统计，自然拿不到那 1 食物。规则条件里没有“被工作”这一项——是使用点的遍历范围决定的，这呼应第二课“控制”与“工作”的区别。

再看一次完整链路：定义在 JSON，加载进缓存，组合进本局规则集；建成建筑时 Unique 对象进入城市的 builtBuildingUniqueMap；算产出时使用点带着 GameContext 查询、逐条套用。静态定义与对局实例的交界就在 updateUniques 这一站：之前的对象全游戏共享，之后的 Map 属于这一局、这一城。

Godot 对照：把效果查询放进结算循环

同样的结构在 Godot 4 C# 里可以这样做：规则模板放共享 Resource（含效果类型、参数、条件）；存档和场景里只存“已建造什么”的 ID 列表；算产出时由一个结算器遍历工作地块，对每个“已生效规则”求值。关键点和 Unciv 一致：规则自己不主动运行，结算器在确定的时机查询它。这样“效果何时生效、对谁生效”由结算代码统一决定，规则只声明内容和条件，新增规则不改动结算循环。

心智模型

  • 规则定义住在 jsons 目录的 JSON 文件里，启动时由 RulesetCache 一次性加载并缓存；对局存档只保存规则集的名字。
  • 每局通过 getComplexRuleset 组合出新的 Ruleset 容器，定义对象与缓存共享同一批实例；约定定义只读，改规则靠模组覆盖。
  • JSON 里的 unique 是字符串，第一次访问才解析成 Unique 对象：placeholderText 压参数查类型，params 供使用点取数。
  • 规则进入对局的桥是 builtBuildingUniqueMap：建成时加入、拆除时重建，并立即重算城市产出。
  • 查询规则都带 GameContext：条件修饰语不满足就跳过，倍率修饰语把一条规则展开成多条。
  • 规则自己不运行；使用点决定何时查询、套在哪些对象上。粮仓只对有人工作的鹿地块生效，正是使用点遍历范围决定的。

城市 A 建成粮仓，工作 2 块鹿地块、1 块小麦地块；城市 B 没有粮仓，工作 1 块鹿地块。哪些地块的产出会多 1 食物？为什么小麦地块不会？拆掉粮仓后立刻打开城市面板，产出还是旧数值吗？

展开答案与分析

选读练习 · 一条拼写错误的规则会发生什么（2 分钟）

模组作者把 "[+1 Food] from [Deer] tiles [in this city]" 写成了 "[+1 Food] from [Dear] tiles [in this city]"。加载会报错吗？游戏里这条效果还在吗？

展开答案

加载不报错——Ruleset.load 只把字符串读进来，不逐条解析；解析是惰性的。解析时模板仍能匹配 StatsFromTiles（占位符的位置没变），所以类型正常，效果也在，只是 params[1] 变成了 "Dear"，永远匹配不到任何地块，规则静默失效。靠规则校验器（RulesetValidator 对照参数类型和已知名字）才能提前发现这类问题；这正是模组界面检查模组链接时要跑校验的原因。
