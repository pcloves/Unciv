第一阶段 / 建立全局模型

一局游戏的数据归谁

上一课看到“下一回合”会复制整局状态、补全运行时数据再结算。这节课把镜头对准这些数据：它们平时挂在谁名下，哪些写进存档，哪些在运行时要重新补上。

需要的基础：Java 对象、集合、引用，以及基础 Kotlin；第一课的 clone 与 setTransients 概念。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标、回顾与场景

做经营或探险游戏时，常会遇到这类问题：界面上的某个数值不对，该去查哪份数据？存了档再读回来，城市为什么找不到自己的地块？为什么敌人单位明明在地图上，玩家却看不见？这节课把一局游戏的数据画成一张“归属地图”，以后读任何代码，都能先判断手头的字段属于哪一类、归谁管。

先找回第一课的主链

NextTurnButton → WorldScreen.nextTurn
  → 后台：clone → setTransients → GameInfo.nextTurn（文明轮转、城市结算）
  → startNewScreenJob → 新 WorldScreen

第一课回答“谁推进回合”，留下两个悬而未决的问题：clone 到底复制了什么？setTransients 补的是什么？本课把这两个问题讲透，顺便看清平时这些数据分别归谁管。第一课选读中关于协程等待的复习题放在本课练习末尾，不在这里展开。

本课的三个问题

  • 数据树：GameInfo、Civilization、City、TileMap、Tile 之间谁持有谁？
  • 存档与引用：哪些字段写进存档，哪些引用在运行时才存在？
  • 视角：同一个世界里，玩家、敌人和观战者看到的数据为什么不同？

读源码时记得问自己：这个字段属于哪一类——对局状态、规则定义，还是运行时引用？三类数据的保存方式和重建方式不同，本课结尾会给出判断口诀。

先认识三个概念

  • 序列化字段：写进存档的字段。它们必须是 ID、名字、坐标、数值等能变成文本的数据，不能是对象引用。
  • @Transient 字段：序列化时忽略，不写进存档；读档后由 setTransients 按保存的 ID、名字、坐标重新补上。
  • 视角（View）：包装同一份状态、从某个文明的角度提供数据。界面通过视角拿数据，而不是直接拿底层对象。

1. 状态树的根：GameInfo

UncivGame.gameInfo 保存着“正在玩的这一局”，而 GameInfo 是这一局所有状态的根：凡是需要写进存档的东西，都挂在这棵树上。

// GameInfo 中与本课相关的字段。

var barbarians = BarbarianManager()
var religions: HashMap<String, Religion> = hashMapOf()
var tileMap: TileMap = TileMap()
var gameParameters = GameParameters()
var turns = 0
var currentPlayer = ""

// 运行时需要的对象不写进存档，读档后由 setTransients 补上。
@Transient
lateinit var currentPlayerCiv: Civilization
@Transient
lateinit var ruleset: Ruleset

civilizations 和 tileMap 是两棵主要的子树：文明管理自己的城市和事务，地图管理全部地块。回合数、当前玩家、开局设置等整局信息也在这里。

ruleset 是规则定义：有什么地形、建筑、单位。它不写进存档，读档时按 gameParameters 里的规则集名字重新取一份。这棵状态树和规则定义的关系，第 3 课专门讲。

注意 IsPartOfGameInfoSerialization：类实现这个接口，表示它可以出现在存档里。它不是普通的标记——文档注释里明确写了序列化规则，比如不能用抽象类型作字段、by lazy 字段必须排除，避免 libGDX 的 JSON 库读到不认识的类型。

// 状态树的主要部分，只画出本课要用的对象。
GameInfo（存档的根）
  civilizations → Civilization（每个玩家势力一份）

读源码时留意实际依赖

状态树描述“谁持有谁”，方便我们找数据，但不代表严格的单向分层。第一课已经看到 GameInfo.nextTurn 接受 UI 进度条参数；反过来，树上的对象也常持有指向根或旁支的运行时引用。遇到交叉调用时以实际代码为准，本课第 3 节会专门看这些引用是怎么补上的。

2. 城市只记坐标，地块只在地图里

先看一个具体问题：玩家查看一座城市，界面要显示中心地块、可工作地块和地块产出。这些地块数据存在哪里？城市的答案很克制：只记坐标，需要时去地图查。

// City 中与本课相关的字段。
// 城市自己的位置只存一个坐标。
var location = HexCoord()
var id: String = NO_ID
override var name: String = ""

// 城市控制的、有人工作的、被锁定的地块，都存坐标集合。
var tiles = HashSet<HexCoord>()
var workedTiles = HashSet<HexCoord>()
var lockedTiles = HashSet<HexCoord>()

// 运行时才补上的引用和缓存，不写进存档。
@Transient
lateinit var civ: Civilization
@Transient
private lateinit var centerTile: Tile  // 缓存，避免每次都查地图
@Transient
lateinit var tileMap: TileMap
@Transient

城市的序列化字段里没有任何地块对象：位置是一个 HexCoord，领土、工作、锁定三套地块都是坐标集合。地块对象本身在地图里，全图只有一份。

tiles 是城市控制的地块（领土），workedTiles 是有人工作的地块。一块地可以先属于城市，但还没有人口去工作它；这个区别在第 14 课讲人口分配时还会用到。

运行时字段 centerTile、tileMap、tilesInRange 都是引用和缓存，读档后重新计算，不写进存档。

TileMap 字段 · L39、L93按坐标取地块 · L222Tile 字段 · L44、L128getOwner · L410

地图的序列化字段只有 tileList 等数据；tileMatrix 是运行时按坐标排好的二维索引。源码注释说它比哈希表查得快得多，代价是读档后要重新填充。

归属关系是反方向的：地块不保存“属于谁”的字符串，而是保存运行时引用 owningCity，指回城市对象。界面想知道地块属于哪个文明时，沿 getOwner() → getCity() → civ 一路找过去。

这条引用链在扩张领土、读档时由 Tile.setOwningCity 建立，第 3 节会看到它发生在 setTransients 的哪一步。

为什么城市不复制地块？

  1. 存档不能存对象引用。地块身上有单位，单位又引用文明和规则集，直接序列化会把整个世界卷进去，还会出现循环引用。存坐标，读档后按坐标找回，链路始终是单向的。
  2. 数据只放一份，才不用同步。如果城市也存一份地块副本，地图上修路、建改良后，城市手里那份不会跟着变。让地块只在地图里，所有修改都发生在同一个对象上。
  3. clone 会换掉所有地块对象。第一课看到每次点“下一回合”都要 clone 整局；TileMap.clone 复制出一批全新的 Tile。若城市保存旧 Tile 的引用，副本里的城市就会指向原地图的地块，结算会改错对象。
Godot 对照：共享模板与实例数据

如果单位、建筑的能力定义放在自定义 Resource 里，多份对象可以共享同一份模板；但“这局游戏里某个单位还剩多少血”是实例数据，得放在每个单位自己的地方。把这两者分开，和 Unciv 把规则集与对局状态分开是同一件事。另外，C# 里把对象图直接 JSON 序列化同样会遇到循环引用，通常也要改成存 ID、坐标，读档后重建。Godot 官方 Resource 说明。

3. 存档存 ID 和名字，运行时引用读档后重建

上一节已经出现多处 @Transient。这一节把它们串起来：跨对象的关系在存档里怎么表示，读档时按什么顺序补上。先看两种典型写法。

// City 中“建城者”的两种表示，摘自不同位置。
// 存档字段：只保存建城文明的 civID。
private var foundingCiv = ""

// 运行时引用：第一次访问时按 civID 从 GameInfo 找回。
@Transient
var foundingCivObject: Civilization? = null
    get() {
        if (field == null && foundingCiv.isNotEmpty())
            field = civ.gameInfo.getCivilization(foundingCiv)
        return field
    }
    set(value) {
        field = value
        foundingCiv = value?.civID ?: ""
    }

// GameInfo 中胜利信息的两种表示。
data class VictoryData(
    val winningCiv: String,  // 存档：赢家的 civID
    val victoryType: String,
    val victoryTurn: Int
) {
    @Transient
    lateinit var winningCivObject: Civilization  // 运行时引用
}

foundingCiv · L73foundingCivObject · L138VictoryData · L86

模式很一致：存档字段保存 ID 或名字，运行时引用用 @Transient 排除，访问或读档时再按 ID 找回。foundingCivObject 的 getter 就是“用到才找”的懒恢复；VictoryData.winningCivObject 则在读档时统一赋值。

单位的“位置”更彻底——它连坐标都不存在自己身上：

// MapUnit 中与本课相关的字段。
// currentTile 是运行时引用：单位站在哪块地上由 Tile 保存，
// 读档时由所在的地块把单位找回，而不是单位另存一份坐标。
@Transient
lateinit var currentTile: Tile

还记得 Tile.militaryUnit 吗？地块保存单位，单位引用地块，这一对关系只在运行时存在；存档里只有“哪个地块上有哪些单位”。

本地 GameInfo.setTransients入口 · L710规则集 · L736地图与文明 · L773、L792

顺序不能乱：城市要用地图查地块，所以 tileMap.setTransients 先执行；地块的邻居缓存依赖坐标索引，所以索引要先填满；setNeutralTransients 处理无主地块的道路归属，要等文明和城市都就位。原方法里每段之间都有“必须在 X 之前”的注释，读的时候值得留意。

City.setTransients 里那句 centerTile = tileMap[location] 就发生在这个过程的文明循环中。这也是第一课 clone → setTransients 的真相：clone 复制数据，setTransients 重建引用。副本里的城市坐标不变，但 centerTile 指向副本自己地图里的新地块。

例外的复制方式：第一课提过 gameParameters 在 clone 时只复制引用；类似地，City.clone 里 toReturn.tiles = tiles 直接共享坐标集合——坐标是值语义的小对象，共享没关系，真正的地块对象由 TileMap.clone 重新复制。

生产经验：惰性缓存和初始化顺序

TileMap.setTransients 先把所有地块填进 tileMatrix，再逐个设置地块的运行时数据。源码注释解释了这个细节：地块的 neighbors 是 by lazy 缓存，第一次访问就会固定下来；如果边填矩阵边初始化，某个地块可能趁索引还没填完就计算邻居，缓存到一份不完整的邻居列表。这类“惰性缓存 + 初始化顺序”的坑在游戏数据里很常见：缓存要慢，重建它必须完整。相关源码 · L611。

4. 同一个世界，不同的观察视角

数据归好位之后，还差一层：谁能看到什么、能做什么。Unciv 的做法是给状态包上“视角”（View）。View 类的文档注释把意图说得很直接：

// View 的文档注释要点（View.kt）。
// View 是玩家能拿到的 API：只提供该玩家有权访问的数据和操作。
// 所有 UI 代码应只通过 View 使用游戏状态。
open class View<T>(protected val wrapped: T,
                   protected open val viewer: Civilization?,
                   val spectatorMode: Boolean = false)

// GameView：从 viewer 文明的视角看一局游戏。
class GameView(gameInfo: GameInfo, viewer: Civilization, ...) {
    val civView = CivView(viewer, viewer, ...)
    val tileMapView = TileMapView(gameInfo.tileMap, viewer, ...)

    // 用不同对象包装同一份状态，数据没有复制。
    fun getCityView(city: City) = CityView(city, viewer, ...)
}

本地 View.kt文档注释 · L6GameView · L11

创建 GameView 时会传入 viewer——当前观察者是谁。之后所有查询都从这个文明的角度回答。界面持有它：

// WorldScreen 中与本课相关的字段。
val gameInfo: GameInfo  // 这局游戏的状态（第一课）
var selectedGameView =
    GameView(gameInfo, selectedCiv, spectatorMode = ...)
// 界面组件从 selectedGameView 取数据。

selectedCiv 在普通游戏里就是玩家文明；观战或回放时可以切换，spectatorGameView 则始终是观战者自己不受战争迷雾限制的视角。同一份 gameInfo 上可以有多个视角。

视角最明显的作用是过滤。看地块视角里的单位：

// TileView 的部分代码。
// 地块上有单位，不等于当前玩家看得见它：
// 对 viewer 不可见的单位返回 null。

        val unit = tile.militaryUnit ?: return null

        return toForeignMapUnitView(unit)
    }

// 底层 Tile 的可见性判定：
// 正在被观测的地块，是文明缓存的可见集合里的地块。

    player.viewableTiles.contains(this)

TileView 过滤 · L58Tile.isVisible · L308viewableTiles · L101

状态里存在，不等于视角里可见。敌方单位始终在 tile.militaryUnit 上；但 TileView.militaryUnit 会先检查它对 viewer 是否可见，不可见就返回 null。战争迷雾就是这样实现的：不是把单位藏起来，而是视角层不给你。

viewableTiles 是文明上的 @Transient 缓存集合，由单位移动、视野计算等环节重算。缓存本身不算对局状态，读档后要重建——这正是第 3 节那张表里的一行。谁在什么时候重算它，第 12 课讲地图显示时再追。

视角还约束操作：CivView 里修改状态的方法都以 try 开头、返回 Boolean 表示是否成功，例如 tryDisableCivConstruction；查询方法则标了 @Readonly。改数据的入口和读数据的入口被有意分开。

回到第一课的概念：GameInfo 是“已经发生什么”，WorldScreen 是“屏幕上显示什么”，中间隔着 GameView——“这个玩家能知道什么”。第一课的状态/规则/推进/视角四栏表里，“视角与显示”那一行，本课补上了它的一半：视角。画面图层（TileGroup 等）是另一半，第 12 课再讲。

排查思路：先分清“状态有没有”和“视角看不看得到”

以后遇到“单位不见了”“地块信息不显示”，先问两件事：状态里真的存在吗（直接看 Tile.militaryUnit 等字段）；视角允许看吗（viewer.viewableTiles、isExplored）。两边都确认过，再去查界面组件有没有创建对应的画面元素。跳过视角直接改界面，常常是白忙。

5. 三类数据与取舍

把前四节收拢成一张分类表。以后每见到一个字段，先判断它属于哪一类，保存方式和重建责任就都清楚了。

类别例子保存方式本课要点
对局状态GameInfo.turns、City.location、Tile.baseTerrain、Civilization.gold写进存档挂在 GameInfo 这棵树上，只存 ID、坐标、数值
规则定义Ruleset：地形、建筑、单位模板不写进存档按 gameParameters 取；第 3 课展开
运行时引用与缓存civ、centerTile、owningCity、tileMatrix、viewableTiles@TransientsetTransients 按 ID、名字、坐标重建

拿到一个字段时问三句：它写进存档吗？改它要不要同步别处？读档后谁负责补上？回答不了第三句，就说明还没找到它的重建入口。

设计取舍：为什么不干脆都存引用？

直接引用省了“查表”这一步，但有三笔账：序列化时要处理重复和循环引用；修改可能发生在副本上，旧引用会悄悄指向错的对象；同一份数据放两处就要维护同步。Unciv 的选择是“存键、查表、热门路径用缓存”：坐标和 ID 是键，tileMatrix、centerTile、neighbors 是缓存。缓存换来了速度，代价是必须跟着状态重建——这也是引用类 bug 的高发区。什么时候可以直接引用？纯运行时结构、生命周期一致、不进存档的对象，比如 GameContext、各种管理器、View 包装。第一课 clone 时 gameParameters 共享引用，就是这个取舍的另一面：判断哪些对象“改了也无所谓”，哪些必须复制。

Godot 对照：数据、模板与画面三层

Unciv 的这套分类可以平移到 Godot 4 C#：对局状态用普通 C# 对象保存，不一定要挂 Node；规则模板用共享的 Resource，注意改模板会影响所有引用者；画面与交互交给节点，节点只负责“呈现视角允许看到的数据”。存档时同样把状态写成 ID、坐标和数值，读档后重建对象引用。差异在于 Godot 的节点树自带生命周期和信号，而 Unciv 的对象树要靠 setTransients 手动重建——第 25、28 课会回到这个话题。

心智模型

  • GameInfo 是存档的根：文明、地图等状态都挂在它下面；规则集和运行时引用不写进存档。
  • 城市只保存坐标和自己的数据；地块全图只存一份，城市按坐标查回地块。
  • 归属关系靠运行时引用：Tile.owningCity 指向城市，再沿 civ 找到文明。
  • 跨对象的引用在存档里写成 ID、名字、坐标，读档后由 setTransients 按顺序重建。
  • clone 复制数据，setTransients 重建引用；副本里的城市坐标不变，但指回副本自己的地图。
  • 状态存在不等于视角可见：GameView 按 viewer 过滤数据，界面通过视角拿东西。

练习 B · 读档后城市怎么找回地块（4 分钟）

新建一局、存档、读档。读档刚结束时，City.centerTile 能访问吗？它是在哪个方法的哪一步被赋值的？如果存档里 location 被改成了地图外坐标，读档会发生什么？

展开答案与分析

反序列化只填序列化字段，centerTile 尚未初始化。重建顺序是 GameInfo.setTransients → Civilization.setTransients → City.setTransients，其中 centerTile = tileMap[location]。坐标越界时，tileMatrix[x - leftX][y - bottomY]!! 会拿到 null 或数组越界，读档直接报错——坐标字段必须保持有效，这也是旧版本迁移要检查坐标的原因（第 25 课展开）。能说出赋值位置和失败方式，说明理解了“存坐标、读档重建”的完整链路。

练习 C · 一份数据还是两份（4 分钟）

假设把 City.tiles 改成保存 Tile 对象引用，并让存档跟着把地块写进城市。举出三个具体会出问题的场景，每个场景对应本课哪一节的哪个原因。

展开核对要点

① 存档重复：同一块地在地图和城市各写一遍，文件变大且两处可能不一致（第 2 节“存档不能存对象引用”）；② clone 失效：第一课每次点下一回合都 clone 整局，旧 Tile 引用会指向原地图的地块，副本里的城市改错对象（第 2 节“clone 会换掉所有地块对象”）；③ 修改不同步：地图上修路、建改良后城市手里那份不更新，必须维护同步逻辑（第 2 节“数据只放一份”）。结论：存坐标加查表，让数据只有一份，重建成本集中由 setTransients 承担。

练习 D · 为什么这块地显示没有单位（选读，3 分钟）

调试时看到 tile.militaryUnit 非空，但界面上该地块没有显示单位。列出两个可能的原因，并给出对应的源码位置。

展开核对要点

① 单位对当前 viewer 不可见：TileView.militaryUnit 里先检查 isVisible(unit)，依赖 viewer.viewableTiles（TileView.kt L58、Tile.kt L308）；② 拿错了视角：观战或回放时界面用的是 selectedGameView，它按 selectedCiv 过滤，与“全知”的 spectatorGameView 不同（WorldScreen.kt L112、L117）。关键结论：状态里存在和视角里可见是两回事，排查顺序是先状态、后视角、再界面。

选读练习 · 第一课回顾（1 分钟）

第一课选读里，PlayTurnAsync 创建一段 Tween 后立即返回 Task.CompletedTask，外层已经写了 await，能保证动画播完才轮到下一位玩家吗？

展开答案

不能。await 到一个已经完成的 Task 会立即继续执行；返回的 Task 必须对应这次动画的完成，例如等待 Tween 的 Finished 信号。判断关键是“这个 Task 在什么时刻完成”，而不是代码里有没有写 await。详见第一课选读。
