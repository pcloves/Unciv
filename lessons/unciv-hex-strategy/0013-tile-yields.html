第三阶段 / 经济专题 · 地基课

一块地怎样变成产出

经济专题的第一课。地图专题留下了一个常驻问题：每块地左上角那几行小数字（粮、锤、金）是怎么算出来的？城市顶部那一排汇总又是谁加的？答案不在一处大公式里，而在两道工序上：TileStatFunctions 先给单格开一张分笔写清的结算单，CityStats 再把该算的格子收进城市、与人口和建筑的其它来源并列，最后落成玩家看到的七个数。这一课把这两道工序走透——后面的人口、建造、文明账本，都只是把这张总结算单往下传。

需要的基础：第三课的 Unique 定义到使用点查询（本课每条加成都走那套）；第六课的 allTerrains 分层与河流公共边（结算单的地形部分直接从这两层摊出来）；第十课起点评价里的农田、矿山、河流（同一批地形作为例子贯穿全课）。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标、回顾与场景

本课的三个问题

  • 单格：一格的产出长什么样，是谁一条条填出来的？
  • 门槛：资源、保底、河流、改良与百分数加成各判了什么条件才生效？
  • 汇总：哪些格进城市，算完在哪一层补，最后七个数落在哪个字段？

读完还要会一件事：不看正文，说出草地+农田+河边这一格，在文明不同科技下各笔加成分别由哪个方法加上。

口述回顾：第三、六、十课

  1. 第三课：粮仓那条 "+1 粮"，从 JSON 定义追到使用点，最后在哪个方法里真正加上？
  2. 第六课：allTerrains 按什么顺序返回？河流信息存在格子的哪一侧？
  3. 第十课：起点评价的三环各查什么、closeStartPenalty 怎么封顶？

1. 单格结算单：getTileStatsBreakdown

玩家往某格一看，弹出 "+2 粮、+1 金"。这个数不是地形 JSON 里现成的，而是 TileStatFunctions.getTileStatsBreakdown 当场拼出来的。它返回的不是一个数，而是一张账目明细：每条来源一行 (来源名, 小计)。全地图、全文明、全界面都走这个入口：

val road = tile.getUnpillagedRoadImprovement()                      // ③ 道路

    listOfStats += getSingleTerrainStats(riverTerrain!!, gameContext) // ⑤ 河边 +1 金
}

    else Stats.ZERO                                                 // ⑥ 城中心保底

脑内模型是柜台开收据：营业员拿一张空白结算单从上往下逐条问——地形票面多少？改良、道路各加多少？这个城市对我这格有没有特别加价？挨着河加不加？保底线要不要补？每条都是一行“名字 + 数”，最后把全 0 的行滤掉、条款拷一份出去（原件可能挂在规则对象上，不能让人改）。后面怎么加，交给拿单的人，他只挑自己关心的行看。

① 地形票面是第六课的 allTerrains 从底（基础地形）到顶（自然奇观、特征）摊出的票面数值，遇 overrideStats（如 Ice）整层替换、遇 NullifyYields 直接只留本层。

②③ 改良与道路各起一个小桶；getUnpillaged… 是“没被掠夺才算”的闸门，废墟不算账。

④ 城市带给本格的 unique 有独立入口，下一块讲。

⑤ 河流不是地形（第九课的三布尔边存储），但产出上和地形同等对待：按规则集里那个虚拟 "River" 地形读票面（G&K 是 gold=1），规则集没这条时退回硬编码的 +1 金。第十课起点评价里的“临河加分”就是这条的另一个消费方。

⑥ 保底只在城中心起，默认 2 粮 1 锤。沙漠城中心票面全 0，靠保底补成 2 粮 1 锤——这是“新开的城不会 0 产出”的来源。

⑦ 资源既不是地形也不是改良，它挂在观察方身上：看见才算（canSeeResource 依科技与规则判定），同一格给不同文明看结论可以不同。

⑧ 改良的额外加成单独一个方法，吃科技、邻近格数与淡水条件，第 2 节展开。

⑨⑩ 汇总前先补保底差值，最后滤掉空行、逐行克隆——注释点名“别改到 uniques/terrains 里的原型 Stats”。

fun addStats(unique: Unique) {
    val tileType = unique.params[1]                              // ④ 点的是谁的名：Farm / Grassland / Road
    if (improvement != null && improvement.matchesFilter(tileType, gameContext))
        improvementStats.add(unique.stats)                       // ⑤ 进改良桶
    else if (tile.matchesFilter(tileType, observingCiv))
        listOfStats.add("{对象名} ({显示文本})", unique.stats)    // ⑥ 进地形票面行
    else if (road != null && road.matchesFilter(tileType, gameContext))
        roadStats.add(unique.stats)                              // ⑦ 进道路桶
}

脑内模型是分拣台：城里每栋建筑、每项政策、每份宗教都往下递纸条，分拣员先看纸条点的是谁的名，再往对应桶里放——同一条“+1 粮”，点名 Farm 就进改良桶，点名 Grassland 就进地形票面。第三课那条粮仓 unique 走的正是这条路。

① StatsFromTiles 的模板是 [+N Stat] from [XXX] tiles [cityFilter]，所以在查之前先过一层 cityFilter——“某座城”和“全部城”就是靠这一行区分，测试里的 statsFromTiles 与 statsFromTilesMultifilter 正钉着这一点。

② StatsFromObject 不卡地形，专门匹配“某个对象名”（某 specialist、某建筑名），本格里任一承载层的名字对上就加。

③ StatsFromTilesWithout 是“本格没有 XX 才加”；G&K 里 Farm 的淡水条件是写在改良自身 unique 上的，这类模板主要留给 mod。

④⑤⑥⑦ 三个桶的优先级简单：改良名对上先走改良，否则看格子的地形/通用名，否则看道路名。一张纸条永远只进一个桶，不会双计。

把这一节落到具体数字上。用同一组场景实测（G&K 规则集、TestGame 全草地小图）：

  • 草地+农田：明细两行 Grassland +2 粮、Farm +1 粮，合计 3 粮。
  • 再加一条河（未研 Civil Service）：多一行 River +1 金，合计 3 粮 1 金；农田仍只加 1 粮。
  • 研出 Civil Service：农田那行变 +2 粮（淡水 unique 生效），合计 4 粮 1 金。注意这一笔来自 getExtraImprovementStats，不是 Farm 票面本身。

2. 逐条相加：地形、改良与道路

结算单的常态是一串独立加数：地形票面 → 改良票面 → 城市进格 unique → 邻近/科技/淡水加成 → 保底。谁都不依赖谁，依次加上。地形叠层与改良加成合在左侧一块看：

// getTerrainStatsBreakdown 与 getExtraImprovementStats 的骨架（部分代码）。
// 问：多处地形的票面怎么合？改良“每邻近一处森林 +1 金”从哪来？
for (terrain in tile.allTerrains) {                              // ① 从底到顶：基础地形→奇观→特征
    val terrainStats = getSingleTerrainStats(terrain, gameContext)
    when {
        terrain.hasUnique(NullifyYields) -> return terrainStats  // ② 只留本层，后面全不算
        terrain.overrideStats -> list = terrainStats             // ③ 本层替换之前所有层
        else -> list += terrainStats                             // ④ 普通情况：往上叠
    }
}

improvement.forEachMatchingUnique(UniqueType.Stats) { unique ->
    stats.add(unique.stats)                                      // ⑤ 改良定义里写死的票面
}
improvement.forEachMatchingUnique(UniqueType.ImprovementStatsForAdjacencies) { unique ->
    val adjacent = unique.params[1]
    val n = tile.neighbors.count {
        it.matchesFilter(adjacent, observingCiv)                // ⑥ 数一数邻近几个 XX
            || it.getUnpillagedRoad().name == adjacent
    }
    stats.add(unique.stats * n)
}
improvement.forEachMatchingUnique(UniqueType.ImprovementStatsOnTile) { unique ->
    if (tile.matchesFilter(unique.params[1])
        || unique.params[1] == Constants.freshWater && tile.isAdjacentTo(Constants.freshWater)
        || unique.params[1] == "non-fresh water" && !tile.isAdjacentTo(Constants.freshWater))
        stats.add(unique.stats)                                  // ⑦ 淡水/非淡水/地形条件
}

脑内模型是一格的几层贴纸：地形本身可能叠多层（草地+森林、海面+环礁），从下往上一层层贴；override 层会把之前整张换掉，Nullify 层说“只留我这一张”。改良则分两种：定义里写死的票面（"+1 粮"），和要现场数条件才给的额外加成。

① allTerrains 的顺序是第六课定的：基础地形 → 自然奇观 → 地形特征。顺序决定“叠加还是替换”。

②③ overrideStats 与 NullifyYields 是两个极端：前者是“本层换掉底下的与之前的特征”（Ice 就是），后者是“只留我一张票”。

④ 默认是简单叠上去——草地+森林就是草地票面（2 粮）加森林票面（+1 锤）。

⑤⑥⑦ 改良的额外加成分成三段，顺序固定：先加定义里的票面；再按邻近格数按比例给（数邻居里匹配的对象，或一条同名道路）；最后按本格条件给（淡水、非淡水、某种地形）。G&K 农场那条 "[+1 粮] from [Fresh water] tiles <after discovering [Civil Service]>" 走的就是 ⑦，条件里还带科技。

3. 三张闸门：可见、保底、加或乘

同一格不会对任何询问者都长出一样的明细。区分“谁来问”的只有三件事：资源可见性、城中心保底、以及百分数乘在哪一行。前两件在结算单里，第三件在 getTileStats 的尾部：

本地 TileStatFunctions.ktgetTileStats · L36保底段 · L102getTilePercentageStats · L192

脑内模型是同一张单给三个观众看：旁观者（observingCiv 为空）只拿到票面——没有资源、没有科技加成；AI 拿到它此刻该有的；人类玩家拿到全部。同一格数值不同，不是格子变了，是观察方变了。保底是另一回事：它是城中心的“不足补满”，只对城中心那一格有效。百分数乘法则在最外层，地形票、改良桶、道路桶各自乘自己那张百分数小计。

① 资源可见性由 Civilization.canSeeResource 判，多数资源要某科技（铁要铁器加工）。实测：同一块小麦格，文明看不见时只按草地算 2 粮，看见后变 3 粮。

② getExtraImprovementStats 是“改良与观察方科技是否达成”的接口，Civil Service、Fertilizer、Scientific Theory 这类条目都从这里进账。

③④ 保底只在城中心。missingFromMinimum 算的是差值而不是把保底又加一遍——草地城中心已满足 2 粮 1 锤就不补，沙漠才补到 2 粮 1 锤。这正是“包底”与“加成”的区别，也是新手常混的一点。

⑤⑥⑦ 百分数加成单独由 getTilePercentageStats 收集，产出一张 TilePercentageCategory → Stats 的 EnumMap。乘法的关键是“每个来源只乘自己归类那一桶的百分数”：地形票上的 +10% 锤不会加到改良桶，改良的 +10% 也不会漏到地形票。分类依据是结算单那一行的来源名（是不是改良名、是不是道路名），其余行一律归 Terrain。

脑内模型是门店对账：本店辖地内，经理只认三类格——店址本格（城中心）、挂牌出工的格（派了人口）、挂了“免人口产出”牌子的格；其它格就算贴着店边，也不进今天这本账。

①② city.tilesInRange 是城市的三环；城中心永远算，不派人口也在账上。实测：人口 1 的首都，statsFromTiles 是 +1 锤 5 粮 = 城中心草地（2 粮，靠保底补到 2 粮 1 锤）+ 派工农田（3 粮）。

③ 派工靠 city.isWorked——一个人口管理器维护的集合。地块所有权（这格是不是我的）与工作（有没有人在这格上干活）是两件事：有主没人干，不进账。

④ 个别改良/地形支持“不派人口也产出”，拥有这类格的城也把它算进来。普通城里很少命中，但代码一并覆盖。

⑤ 被封锁的格：产出不给，人口也被提出来等重新分配——这是一次行为，不是数值修正。

⑥⑦ 每个工作格都调 getTileStats(city, civ) 拿合计，连续 add 进 statsFromTiles。这是地块对城市的唯一收入管道，没有第二处“人工再汇总一遍”。

脑内模型是月底结账：出纳先点完工位（updateTileStats，地块进账的唯一管道），柜台再逐项叠上人口、建筑、专家、贸易路线、城市 unique。这些原值先放进 baseStatTree；随后按比例调整——statPercentBonusTree 收齐黄金年代（+20% 锤和文）、傀儡城（−25% 科学与文化）、兵力不足（产锤惩罚）等百分数来源；最后逐项落乘数，再处理维护费、余粮转生产、生产转科学、被占期间的清空等特殊规则。

① statsFromTiles 在这一步算好，下面才可能被引用。

②③④ 建筑、专家、按来源分的城市 unique 一次性算好往下传——源码注释点名这几步“贵”，同一份输入不重复算。

⑤⑥⑦⑧ 顺序有依赖：先有地块票面才能算快乐度（地块的 happiness 参与）；先有快乐度与百分数树，才能落最终乘数。源码注释里那段“食物计算很绕”说明了为什么余粮与增长加成要放到最后单独处理。

⑨⑩ currentCityStats 是给界面读的最终七数；update 的最后一脚把改动推给文明层（第 16 课展开）。实测：人口 1 首都 currentCityStats = +1 锤 3 粮 1 科学（Population 行给 −2 粮 +1 科学，地块给 +1 锤 5 粮）。

update 的触发面很广：人口变了、地块变了、建造队列变了、科技变了，任何一项变化都会推一次 update。所以玩家不需要懂所有公式，也不会因为多修一条路而看不见加成——所有变化都收束到同一条链：updateTileStats → update → currentCityStats。

5. 追一次改良完成与科技解锁

把两个最常问的场景串起来：① 农场修好了；② 研究出 Civil Service。两个动作都不直接改数字，而是改条件，等下一次重算才体现：

// 修建完成 → 科技解锁（各方法分散在几个类，按时间顺序拼排）。
// 问：农场修好后这一格怎么变 3 粮？研出 Civil Service 后又怎么变多？
// 修建完成：
tile.improvement = "Farm"                                         // ① 落到格子上
tile.setTerrainTransients()                                       // ② 重建瞬时索引（含 allTerrains）

// 城市侧任一变化都会推 update：
updateTileStats()                                                 // ③ 所有工作格重算一遍
tile.stats.getTileStats(city, city.civ)                           // ④ 本格：地形票 + Farm 票面
updateFinalStatList(...)                                          // ⑤ 全链落乘数
currentCityStats = ...                                            // ⑥ 界面读到 +3 粮

// 研出 Civil Service：
civ.tech.addTechnology("Civil Service")                           // ⑦ 科技入账（此时不动地块）
city.cityStats.update()                                           // ⑧ 下次重算时条件才生效
getExtraImprovementStats(...)                                     // ⑨ Farm 淡水 unique 命中，+1 粮

本地 TileStatFunctions.ktgetExtraImprovementStats · L294CityStats.update · L485

脑内模型是换了招牌，重开发票：修完农田不是“写下 +1”，而是招牌换了；研出科技不是“马上 +1”，而是条件从 false 变 true。两件事的下一瞬间都不动产出本身，一切交给下一次重算重新开发票。这样所有变化只走同一条链，不会出现“科技进来时手动补一笔”的旁路。

①② 改良落到格子并重建瞬时索引，此时结算单还等着重算。

③④ 重算时逐格取结算单——农田票面 +1 粮进来，合计从 2 粮变 3 粮。

⑤⑥ 城市重算后 currentCityStats 更新，界面下一帧显示 +3 粮。

⑦ 科技入账本身不改地块，只让 Farm 的淡水 unique 条件成立。

⑧⑨ 下一次重算时 getExtraImprovementStats 命中该 unique，农田行由 +1 变 +2 粮。实测：同一格合计由 3 粮 1 金变 4 粮 1 金。这类“条件型加成”是经济系统最容易被漏看的部分——数字不涨时，先查是不是少了哪个条件、或还没触发重算。

心智模型

  • 单格是结算单：getTileStatsBreakdown 逐笔写清“来源名 + 数”；getTileStats 在尾部补保底差值、再逐桶乘百分数，最后汇总成玩家看到的数。
  • 三桶分拣：城市的加成按“点谁的名”进地形票面、改良桶、道路桶；一条 unique 只进一个桶，不会双计。
  • 保底是补差不是加成：城中心默认 2 粮 1 锤，只补到够，沙漠变 2 粮 1 锤靠的就是这一行。
  • 百分数按桶分开乘：地形票、改良桶、道路桶各乘自己那张小计，不会把改良的 +10% 漏到地形票上。
  • 地块收入是单向管道：updateTileStats 逐格 add 出 statsFromTiles；update 再经 baseStatTree（原值）→ statPercentBonusTree（百分数）→ finalStatList（落乘数/维护费/转化）→ currentCityStats（界面读）四步落定。
  • 条件挂在观察方：资源可见、科技是否已研都以 observingCiv 为输入；同一格给不同文明看数值可以不同，不是格子自己变了。

展开核对要点

练习 C · 乘在哪一层（5 分钟）
