第一阶段 / 建立全局模型

下一回合由谁推进

点击“下一回合”后，游戏到底做了什么？这节课沿着源码往下读，看看界面如何发起结算，各个文明和城市又是按什么顺序处理的。

需要的基础：Java 对象、集合、引用与线程，以及基础 Kotlin。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标与场景

做经营或探险游戏时，常会遇到这样的问题：玩家点了“进入下一天”，粮食要结算，人口可能增长，建筑可能完工，其他势力也该行动了。这些事由谁调用、先做哪件？我们借 Unciv 的“下一回合”看一套实际做法。以后再读地图和经济系统，就能知道它们在整个流程中负责哪一部分。

先认识三个游戏概念

  • 文明：本局中的一个玩家势力，可以由人控制，也可以由 AI 控制。
  • 城市：属于某个文明，管理自己的人口、建造项目和各项产出。
  • 回合：各文明轮流行动并结算；一个文明结束行动，不一定意味着整局的回合数加一。

这节课先跟着人类玩家点击“下一回合”的常见情况读。读到每一步时，记得问自己：正在处理哪个文明的数据？是在开始回合，还是结束回合？具体经济公式、战斗细节和联机异常处理，后面再展开。

2. 点击这个按钮，不一定会进入下一回合

前面截图的右上按钮要求选择建造项目。这个按钮会根据当前局面做不同的事，所以我们要先看看，它现在会调用哪个方法。

// NextTurnButton 中处理点击、选择动作的部分代码。
onActivation { nextTurnAction.action(worldScreen) }

    NextTurnAction.entries.first { it.isChoice(worldScreen) }

// NextTurnAction 中的 NextTurn 分支。
override fun isChoice(worldScreen: WorldScreen) = true
override fun action(worldScreen: WorldScreen) =
    worldScreen.confirmedNextTurn()

NextTurnButton.kt · L32、L83NextTurnAction.kt · L134

entries.first { ... } 按枚举声明的顺序，选择第一个满足条件的动作。前面的“选科技”“选生产”等条件都不满足时，才会轮到末尾总是返回 true 的 NextTurn 分支。

confirmedNextTurn 会根据设置决定是否弹出确认框，确认后调用 nextTurn()。它是 WorldScreen 的扩展函数，代码却写在 NextTurnAction 中。读 Kotlin 时要留意：看起来像成员方法的调用，也可能是扩展函数。

另外，NextTurnButton.update 还会设置 isEnabled。如果正在自动存档，或者上一回合还没算完，按钮可能处于禁用状态。

排查思路：先确认代码有没有执行到

遇到“按按钮后没结算”，可以先查三件事：按钮是否可用？当前选中了什么动作？有没有调用 WorldScreen.nextTurn？确认已经进入结算，再去查经济公式。在 Godot 中排查类似问题时，也可以先检查信号是否连接、回调是否执行，以及哪个条件让流程提前结束。

3. 复制一份游戏状态，在后台计算下一回合

进入 WorldScreen.nextTurn 后，游戏会复制当前状态，在后台线程中计算下一回合。下面只保留主要流程，省略了进度条初始化、联机上传和异常处理。

// WorldScreen.nextTurn 的主要流程。
isPlayersTurn = false
shouldUpdate = true

nextTurnUpdateJob = Concurrency.runOnNonDaemonThreadPool("NextTurn") {
    val originalGameInfo = gameInfo
    val gameInfoClone = originalGameInfo.clone()
    gameInfoClone.setTransients()

    gameInfoClone.nextTurn(progressBar, true)

    // 如果玩家在等待时打开了另一局游戏，就结束这个后台任务。
    // 避免下面的代码把界面切回原来那一局。
    if (game.gameInfo != originalGameInfo)
        return@runOnNonDaemonThreadPool

    startNewScreenJob(gameInfoClone, autoPlay)
}

按执行顺序看这三步

  1. 暂停改变局面的操作。玩家暂时不能继续下指令，但仍然可以浏览地图。
  2. 在副本上结算。先复制状态，再补全对象引用等运行时数据，然后计算下一回合；原来的状态仍供界面显示。
  3. 算完后再更新界面。先检查玩家有没有打开另一局游戏；如果已经换了，就结束任务，否则用算好的状态创建新界面。

回头看第一节的对象关系，就容易理解了：按钮属于界面，实际改变的是 GameInfo 的副本，最后界面再显示这份新状态。

这里把结算放在后台，不等于 UI 也能随便放到后台。libGDX 的 OpenGL 操作必须在渲染线程执行，Scene2D 组件也不能随意从多个线程访问。

libGDX 官方线程约定项目文档 · NextTurn 的克隆动机

深入一点：结算代码同步执行，UI 为什么还能更新？（选读，约 8 分钟）

同步执行只说明调用顺序，不说明运行在哪个线程。GameInfo.nextTurn 中的 startTurn、automateTurn、endTurn 确实依次执行，但这段工作在后台线程上进行，渲染线程没有停下来等它算完。

协程藏在外面的工具方法中

继续跟进 Concurrency.runOnNonDaemonThreadPool，可以看到它调用 run，再经过 launchCrashHandling 调用协程的 launch。调度器 Dispatcher.NON_DAEMON 则来自 Java 线程池：

// Concurrency.kt 中创建线程池调度器的部分代码。
val executor = Executors.newCachedThreadPool(object : ThreadFactory {
    // ...省略线程命名及守护线程设置...
})
return CrashHandlingDispatcher(executor.asCoroutineDispatcher())

协程负责把外层任务安排到这个线程池；其中调用的普通函数仍然可以是同步函数。就像 Java 中把一段按顺序执行的代码交给 ExecutorService：这段代码没有变成多段并行任务，但提交任务的 UI 线程可以继续处理自己的工作。

所以不用给 startTurn、automateTurn、endTurn 各套一个协程。反过来，只给函数加上 suspend 也不会自动让它去后台运行；这里真正决定线程的是调度器。

结算时通知进度，界面有空时更新

WorldScreen.nextTurn 在启动后台任务前创建 NextTurnProgress，并调用它的 start(this)。这个进度条对象随后作为参数传给 GameInfo.nextTurn，再传到 TurnManager。例如，在处理城市时：

// TurnManager.startTurn 中的城市循环。
for (city in civInfo.cities) {
    progressBar?.increment()
    CityTurnManager(city).startTurn()
}

这里调用 increment 后直接处理城市，不会等进度条画出来。再看进度条类中的实现：

// NextTurnProgress 中的部分代码。
fun increment() {
    progress++
    startUpdateProgress()
}

private fun startUpdateProgress() {
    isDirty = true
    Concurrency.runOnGLThread {
        updateProgress()  // 在渲染线程中修改进度条。
    }
}

runOnGLThread 使用另一个调度器 Dispatcher.GL。它最终通过 Gdx.app.postRunnable(block) 把任务交给渲染线程。根据 libGDX 的约定，这类任务在后续一帧的 render 调用前执行；屏幕的 render 再通过 stage.act() 和 stage.draw() 更新、绘制 UI。

后台线程：城市 A → increment → 城市 B → increment → 继续结算
                         │                  │
                         └─ 请求更新进度 ────┘
                                  ↓
渲染线程：处理输入 → 执行排队的 UI 更新 → 更新动画、绘制画面 → 下一帧

后台不用等待这一帧画完，渲染线程也不用等待整轮结算完成。

当前这条流程显示的是 Working... 状态和进度条，并没有在每个 AI 回合开始时传入文明名称。进度主要按城市的开始、结束处理次数估算，也不等于“已经用掉的时间百分比”。

如果要等动画播完，又是另一种需求

“正在处理某文明”是一条进度通知：后台可以发完就继续算。但“角色走到目的地后，才开始下一次攻击”要求先后配合，不能只通知一下就继续执行。

一般有两种做法：让执行流程等待动画完成的信号，再处理下一步；或者先算出结果和动作记录，再由表现层按顺序播放。它们是可选设计，不是上面这条 Unciv 进度条流程的实现。

还有一个容易忽略的细节：把“正在处理 A”交给 UI 后，后台可能很快就算完 A，又开始 B。通知已经发出，并不保证玩家一定看到 A 的文字。如果要求每条提示都展示出来，或要求动画完整播放，就要另外控制显示顺序和时长。

Godot 对照：后台计算，主线程改节点

在 Godot 4 C# 中也要分清这两件事：后台任务可以计算自己负责的数据，修改活动场景树中的 Label、进度条等节点则要交回主线程。可以通过 CallDeferred 安排节点更新；它同样不表示“调用返回时画面已经显示”。参见 Godot 官方线程说明。

设计延伸：播完当前玩家的动画，再进入下一个玩家的回合（选读，约 10 分钟）

前面已经看到，progressBar.increment() 只请求 UI 更新，结算不等它完成。如果游戏要求“播完 A 的回合，再计算 B 的回合”，就需要在两个玩家之间加入等待。

问题不在 while，而在循环中没有等待表现完成的步骤。Unciv 当前的 GameInfo.nextTurn 把多个 AI 的回合连续算完，调用者要等整个方法返回后才能接着做事。在外面等待这个方法结束，无法把等待点插到它内部的两个 AI 之间。

把一次计算缩小到一个玩家

针对“每个玩家播完再继续”的需求，可以把回合循环放到一个负责流程的对象中，例如 TurnController。它调用规则层算出当前玩家的结果，调用表现层播放，再切换玩家。规则层不需要知道 Tween、节点或动画时长。

// C# 设计示意：下面这些游戏方法是示例，不是 Unciv 的现有 API。
// 假定从 Godot 主线程调用，且已经轮到第一个 AI。
async Task RunAiTurnsAsync()
{
    while (game.CurrentPlayer.IsAi)
    {
        // 只计算当前 AI：startTurn → automateTurn → endTurn。
        // 返回这次发生的动作和数值变化，暂时不切换玩家。
        TurnResult result = game.ExecuteCurrentTurn();

        // 这次播放的动画全部结束后，才继续执行下面的代码。
        await presenter.PlayTurnAsync(result);

        game.MoveToNextPlayer();
    }
}

game 管理状态并计算规则；presenter 操作节点、播放动画；外面的 RunAiTurnsAsync 决定执行顺序。等待发生在这个外层流程中，不需要让伤害计算、人口增长等规则方法都改成异步。

为了突出等待的位置，示例假定单次计算足够短，直接在主线程执行。若 AI 计算很重，可以把纯数据计算交给后台任务并等待结果，再回主线程播放。前提是后台拥有独立的数据访问权，不能把会访问 Godot 节点的代码直接塞进 Task.Run；async 本身也不会让计算自动去后台。

循环停下来，主线程不会停下来

执行到 await 时，如果播放还没完成，当前异步方法会暂时返回，把执行机会交还给引擎。Godot 继续处理每一帧、推进 Tween、绘制画面。等播放任务完成，这个方法才从 await 后面继续，执行 MoveToNextPlayer。

计算 A 的回合
    ↓
开始播放 A 的动画
    ↓
await：回合流程暂时不往下走；Godot 继续逐帧更新
    ↓
A 的动画全部结束，播放任务完成
    ↓
切换到 B，再计算 B 的回合

不要在主线程用 Task.Wait()、.Result 或 Thread.Sleep 来代替这个等待。动画依赖主线程逐帧推进，把线程堵住后，动画也无法正常结束。C# 的 await 官方说明明确区分了“暂时停止异步方法”和“阻塞线程”。

PlayTurnAsync 到底什么时候算完成？

这个方法返回的 Task 必须代表本次表现已经完成，而不是“已经提交 UI 任务”或“已经创建 Tween”。例如，下面这个方法属于表现层中的 Node 脚本，在主线程执行：

// Godot 4 C#：正常播放一段有限时长的移动动画。
// 假定播放期间节点有效，Tween 不被中断。
async Task PlayMoveAsync(Node2D view, Vector2 destination)
{
    var tween = view.CreateTween();
    tween.TweenProperty(view, "position", destination, 0.3);

    // 创建 Tween 不代表播放结束，Finished 才表示它正常播完。
    await ToSignal(tween, Tween.SignalName.Finished);
}

整回合有多个动作时，PlayTurnAsync 可以依次等待每个动作的播放任务；允许同时播的动画，则要等这一组都完成后再返回。如果没有需要显示的动作，播放任务可以直接完成。

同样地，即使用 join 等到了某个 GL 调度任务结束，如果那个任务只调用了“开始动画”，也仍然没有等到动画结束。在 Kotlin 中，可以让外层回合方法成为 suspend 函数，并调用真正等待动画完成的挂起函数；原来的同步 nextTurn 内部不能凭空多出这种等待。

结果已经算完，动画怎样保留过程？

假设 A 的单位先从格子 1 走到格子 2，再攻击 B。整回合算完时，逻辑位置已经是格子 2，B 的血量也已经扣了。若界面每帧都直接读取最终位置和血量，就会先瞬移、先掉血，再补播动画。

因此，TurnResult 要保留播放所需的过程数据，例如单位 ID、起点、终点、攻击目标、扣血前后的数值。表现层按这些记录推进画面，播完后再与这一回合的最终状态对齐。这些记录应保存当时的值，不能只是引用后面还会变化的单位对象。显示动画时也不要再算一次伤害或再执行一次移动规则。

需要在哪一步停，就把计算拆到哪一步

需求安排方式
A 的回合播完，才计算 B计算一个玩家 → 等待整回合表现 → 切换玩家
每走一步都要等动画，可能还要玩家选择计算一个动作 → 等待表现或输入 → 决定下一个动作
只要求画面依次播放，逻辑可以提前算完先计算并记录多个回合，再按顺序播放记录

第三种也能让玩家看到“A 播完再播 B”，但不满足“B 的逻辑也必须等 A 播完才开始”。如果中途的玩家输入可能改变后面的结果，就不能事先把那些结果都算死。

不使用 async/await 时，也可以显式保存“计算中、播放中、等待输入”等状态，收到播放完成的回调后再切换状态。两种写法都要保存当前玩家和执行进度；简单的顺序流程用 async/await 更容易看清先后关系。

落地时补上跳过和退出处理

跳过动画时，表现层应直接显示本次结果并完成播放任务；退出对局时，则应取消整个流程，不能恢复后又开始下一位玩家。不要假定 Tween 被 Kill 或节点被释放后，正常完成信号仍会到来。还要防止按钮连点启动两套回合循环。上面的短例子只展示正常完成的过程。

为什么 clone 之后还要 setTransients？

// GameInfo.clone 的部分代码。
val toReturn = GameInfo()
toReturn.tileMap = tileMap.clone()
toReturn.civilizations = civilizations.asSequence()
    .map { it.clone() }
    .toCollection(ArrayList(civilizations.size))
// ...省略其他字段的复制...
toReturn.gameParameters = gameParameters

// 再看 GameInfo.setTransients 中的两处赋值。
tileMap.gameInfo = this
// ...省略旧存档和模组名称的兼容处理...
ruleset = RulesetCache.getComplexRuleset(gameParameters)

新复制出的 GameInfo 还不能直接拿来运行。例如，地图需要知道自己属于哪个 GameInfo，对局也需要找到要使用的规则集。上面两处赋值就在补上这些引用。setTransients 还会重算缓存数据，并处理旧存档的兼容问题。

clone 不保证所有字段都被深拷贝。地图和文明分别调用了自己的 clone()，但 gameParameters 只是把引用赋给副本，两个字段仍然指向同一个对象。想判断某个对象能否独立修改，需要继续检查它的复制方式和使用位置。

先记住这里的顺序：复制状态 → 补全运行时数据 → 计算下一回合。第二课会接着讲对象之间的关系，第 25 课再详细讲读档和兼容处理。

设计取舍：什么时候值得复制状态？

Unciv 在这条下一回合流程中复制整局，是为了让后台结算和前台显示分别使用各自的状态。这不代表每次点击或移动都要复制，更不代表 Godot 即时经营游戏应该每帧复制整个世界。做自己的游戏时，先明确哪些数据会在后台修改、界面什么时候读取结果，再根据数据量决定复制哪些内容、多久复制一次。

4. 轮到哪个文明，就处理哪个文明的回合

接下来进入 GameInfo.nextTurn，重点变成了“下一个轮到谁”。为了看清主流程，下面简化了原方法：假定所有玩家都还在场，暂时不考虑模拟、战败、观战和联机的特殊情况。

// GameInfo.nextTurn 的简化版本，仅用于理解文明的处理顺序。
var player = currentPlayerCiv
var playerIndex = civilizations.indexOf(player)

fun setNextPlayer() {
    playerIndex = (playerIndex + 1) % civilizations.size
    if (playerIndex == 0) turns++
    player = civilizations[playerIndex]
}

if (player.isHuman()) {
    TurnManager(player).endTurn(progressBar)
    setNextPlayer()
}

while (player.isAI()) {
    TurnManager(player).startTurn(progressBar)
    TurnManager(player).automateTurn()
    TurnManager(player).endTurn(progressBar)
    setNextPlayer()
}

currentPlayer = player.civID
currentPlayerCiv = player
TurnManager(player).startTurn(progressBar)

遇到人类玩家时停下来

先结束当前人类玩家的回合，再逐个处理后面的 AI。轮到下一位人类玩家时，调用他的 startTurn 做好准备，然后把操作机会交给他。

注意 GameInfo.turns：只有文明列表的索引回到 0 时，它才加一。所以调用一次 nextTurn，整局的回合数不一定增加；后面两个相邻的人类玩家就是一个例子。

原方法的 while 条件还包含模拟、战败玩家和观战等情况。分析这些场景时，需要回到原方法看完整条件。

TurnManager(player) 创建的是一个管理器，传入的是已有的文明对象。接下来的方法都在处理这个文明，没有重新创建一个文明。

5. 文明先处理收支，再逐个处理城市

沿 TurnManager.endTurn 继续读，会看到“计算本回合收支”和“修改国库余额”是分开的。下面只列出相关调用，保留它们在原方法中的先后顺序，具体公式留到经济专题再讲。

// TurnManager.endTurn 的部分代码。
// 先更新文明的各项产出汇总。
civInfo.updateStatsForNextTurn()
// ...省略获取 nextTurnStats 和处理破产的代码...
// 将本回合的黄金净变化计入国库。
civInfo.addGold(nextTurnStats.gold.toInt())

// ...科技、宗教、间谍等处理...
for (city in civInfo.cities.sortedByDescending { it.isBeingRazed }) {
    progressBar?.increment()
    CityTurnManager(city).endTurn()
}
// ...临时效果、黄金时代、单位和外交等后续处理...

算出收支，不等于已经入账

updateStatsForNextTurn 更新计算结果；addGold 才会修改国库中的黄金数量。比如本回合黄金净收益为 10，先算出这个 10，之后再把它加到余额上。若净收益为负，入账时余额就会减少。

看调用顺序：addGold 在城市 endTurn 循环之前。分析某项变化会不会影响这次入账时，必须按源码中的顺序推演，不能先假定“所有城市算完，再统一加钱”。

sortedByDescending 把正在夷平的城市排到前面，源码注释说明这是为了解决地块归属问题。排序还会生成一份新列表，这样即使结算时有城市被移除，也不会一边遍历原列表一边修改它。

城市又把工作交给自己的管理器

// CityTurnManager.endTurn 的部分代码。
val stats = city.cityStats.currentCityStats
city.cityConstructions.endTurn(stats)

// ...省略宗教处理、城市回血和人口分配调整...

currentCityStats 缓存着城市当前的各项产出。调用 CityStats.update 时，会重新计算并替换这份结果。它记录的是产出，不是城市已经存了多少粮食，也不是文明的国库余额。

城市的建造、扩张和人口各有自己的处理方法。CityTurnManager 按顺序调用这些方法，把一座城市的回合处理串起来。

有个时机值得留意：城市在 endTurn 中累积生产力，到 startTurn 才检查能否完成建造。源码注释解释了原因：如果新单位在回合结束时出现，敌人就可能先行动，玩家还没来得及控制它，它就遭到攻击了。

Godot 对照：“每天结算一次”还不够具体

假设做一款门派经营游戏：新弟子先加入再分配工作，他今天可能就有产出；若粮食结算后才加入，结果就不同。这是我们自己的设计例子，但和上面的单位生成有相同的问题：事情发生的顺序会影响玩法。用 Godot 实现时，应明确规定这些步骤的顺序，而不是让它取决于几个节点的定时回调恰好谁先执行。

    && gameInfo.turns % UncivGame.Current.settings.turnsBetweenAutosaves == 0

这里的 loadGame 接收已经算好的 GameInfo，用它重新创建游戏界面，并不需要再从磁盘读一遍存档。

UncivGame.loadGame 在 withGLContext 代码块中创建新 WorldScreen，让这部分图形操作在渲染线程执行。满足条件时，还会恢复原来的地图缩放和滚动位置。如果是多个人类玩家在同一台设备上轮流玩，则会先显示玩家准备界面。

最后，游戏根据回合间隔决定是否自动存档。还记得第二节的按钮启用条件吗？这里的 waitingForAutosave 就是其中之一：自动存档没结束时，不能再次推进回合。

心智模型

  • GameInfo 管这一局的数据，UncivGame 管应用和界面。
  • 同一个按钮可能执行不同动作，点击它不一定会进入下一回合。
  • 下一回合先复制状态、补全运行时数据，再在后台计算，最后更新界面。
  • GameInfo 决定轮到谁，TurnManager 处理该文明的回合，CityTurnManager 处理其中每座城市。
  • 算出产出和实际入账是两步，调用顺序会影响游戏结果。
  • 文明列表的索引回到首位时，GameInfo.turns 才加一。

选读练习 · 同步代码一定会卡住画面吗？

假设某个 AI 的 automateTurn 连续计算了两秒，中间没有挂起：画面一定会停止刷新吗？如果改成在渲染线程直接调用它，又会怎样？

展开答案

在当前流程中，它运行在后台线程，渲染线程可以继续刷新，所以画面不必停止；只是这两秒里没有新的进度通知时，进度条可能暂时不动。若改为在渲染线程直接计算两秒，就会占住该线程，期间它无法正常处理后续 UI 更新和绘制。判断关键是运行线程，而不是函数有没有 suspend。

进一步想想：如果先给 UI 发一条“正在处理 A”，马上继续计算 B，能保证 A 的文字至少显示一帧吗？不能，安排更新和完成绘制之间还有时间差。

选读练习 · await 的对象真的代表动画结束吗？

PlayTurnAsync 创建一段 Tween 后，立即返回 Task.CompletedTask。外层已经写了 await presenter.PlayTurnAsync(result)，能保证播完后才轮到下一位玩家吗？

展开答案

不能。外层等到的是一个已经完成的 Task，会立即继续执行。表现层必须让返回的 Task 对应这次动画的完成，例如正常播放时等待 Tween.Finished，再返回。要检查的是“这个 Task 在什么时刻完成”，而不只是代码有没有写 await。
