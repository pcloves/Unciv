第三阶段 / 经济专题 · 文明收支

城市怎样进入文明账本

新单位刚训练完成，黄金的每回合收入减少了，国库却没有立即少钱。这两个读数并不矛盾：一个表示按当前局面计算的净流量，另一个保存已经结算和花费后的余额。本课从城市产出明细出发，追到文明汇总、维护费、幸福度反馈，再确认哪一行代码真正改变国库。

源码基线：1df6249a41301056ddc4448a95a93ddf5403e061；核对日期：2026-09-24。数值场景采用 G&K 规则、Prince 难度的人类文明。代码为真实源码的部分摘录，中文注释为教学所加；折行、省略和教学改写均在块内说明。

目标、回顾与场景

读完要能做什么

  • 从一个城市的最终明细追到文明黄金净流量，指出三类维护费各在哪里计算。
  • 区分统计刷新、幸福度变化和国库入账，解释为何反复刷新不会反复收钱。
  • 把上一课的新单位生成接到收支时间线上，手算生成前后两次国库结算。

把旧课接上来

第 13 课已经得到 finalStatList 和 currentCityStats；第 14 课把净粮食加到存粮；第 15 课说明普通生产在结束时加进度、下次本方开始时完成。

本课随读随回顾：城市每回合产出不是库存，生产进度达到成本也不等于单位已经存在。带着这两点直接往下看。

下面使用两座城市。甲城每回合黄金收入为 8.5、建筑维护费为 2；乙城收入为 5.25、建筑维护费为 1。文明还维护一格费用为 1 的道路，拥有 4 个普通单位，国库为 100。没有贸易、全局黄金奖励、折扣或驻军免维护规则。甲城正在训练第 5 个单位，成本 40、进度 35，本次最终生产力 12.4。

这是为手算而设置的教学场景，收入来自测试中创建的建筑。单位维护公式的游戏进度先固定为 0；两城人口、黄金来源和道路均保持不变。我们调用真实回合管理器验证，暂不推进整局回合数，避免把单位数量变化和时间增长混在一起。

  1. 城市计算保存分来源的最终产出与建筑维护费。
  2. 文明汇总合并各城明细，再加入单位、道路等文明收支。
  3. 更新预测保存当前净流量；幸福度跨过规则边界时重算城市。
  4. 回合结算文明结束回合时取黄金整数部分，调用 addGold。

建议时间：场景与回顾 5 分钟；第 1～2 节 12 分钟；第 3 节 10 分钟；第 4～5 节 12 分钟；心智模型与练习 12～15 分钟。折叠扩展与本地重跑可另选时间。

2. 维护费不是在每次刷新时直接扣国库

维护费先成为统计中的负数，等黄金净流量整体入账时体现为少收或净支出。下表按计算位置区分三类费用；不是按 UI 上可能显示的先后顺序排列。

费用计算入口与来源行需要注意的规则
建筑维护费CityConstructions.getMaintenanceCosts → 城市 Maintenance 行跳过免费建筑，应用匹配的维护费修正；城市层加上适用的 AI 修正后取整数。加入最终明细的位置在产出百分数修正之后。
道路维护费getTransportationUpkeep → 文明 Transportation upkeep 行检查所属城市地块，跳过城中心、没有完好道路的格和规则免维护的格；另处理本文明负责的中立道路。按道路规则读取费用，并应用维护费修正。
单位维护费getUnitMaintenance → 文明 Unit upkeep 行按单位集合、免费名额、折扣、游戏进度和 AI 修正计算，再向零截断为整数。

for (unique in civInfo.getMatchingUniques(
        UniqueType.FreeUnits, civInfo.state)) {
    freeUnits += unique.params[0].toInt()
}
// ② 省略：按免维护条件过滤单位；为每个剩余单位
// 从 1f 开始依次乘适用的折扣，放入 costsToPay。

costsToPay.sortDescending()                // ③ 优先免掉较贵的
val numberOfUnitsToPayFor = max(0.0,
    costsToPay.asSequence().drop(freeUnits)
        .sumOf { it.toDouble() }).toFloat()

// ④ 时间越往后，费用公式越高；进度最多取 1
val turnLimit = civInfo.gameInfo.speed.numTotalTurns().toFloat()
val gameProgress = min(civInfo.gameInfo.turns / turnLimit, 1f)
var cost = baseUnitCost * numberOfUnitsToPayFor * (1 + gameProgress)
cost = cost.pow(1 + gameProgress / 3)

if (!civInfo.isHuman())                    // ⑤ AI 修正与取整
    cost *= civInfo.gameInfo.getDifficulty().aiUnitMaintenanceModifier
return cost.toInt()

3. 幸福度先汇总，再反馈到城市

文明幸福度不能直接取所有城市 currentCityStats.happiness 相加。城市数量、人口造成的不满与难度基础幸福度等另有来源。代码通过 getHappinessBreakdown 单独汇总，然后把结果存到 stats.happiness。

// getHappinessBreakdown 的部分代码。
val statMap = HashMap<String, Float>()
statMap["Base happiness"] =
    civInfo.getDifficulty().baseHappiness.toFloat() // ① 难度基础值

// ② 省略：奢侈品、城邦奢侈品与保留交易幸福度的规则。

for (city in civInfo.cities) {
    // ③ 合并城市专门的幸福度明细
    for ((key, value) in city.cityStats.happinessList.toList())
        statMap[key] = value + (statMap[key] ?: 0f)
}
// ……省略道路规则可能产生的幸福度维护费
for ((key, value) in getGlobalStatsFromUniques())
    statMap[key] = value.happiness + (statMap[key] ?: 0f) // ④ 全局效果
return statMap

② 奢侈品供应等在文明层计算。本节先固定为没有这些来源，资源供应的取得留到第 17 课。

正幸福度与黄金时代：还有一份真正累积的数值

GoldenAgeManager.storedHappiness 与 civ.getHappiness() 是两个数。未处于黄金时代时，endTurn(happiness) 把当前幸福度加到 storedHappiness，最低截到 0；负幸福度会减少已有积累。超过所需阈值后进入黄金时代。处于黄金时代时，管理器减少剩余持续回合，不继续按这条路径积累幸福度。

文明在城市结束处理之后才调用这个管理器。进入黄金时代会更新城市统计，当前实现提供生产力与文化加成；这是后续统计变化，不能回头再给刚刚结算过的黄金或建造进度加一次。某些政策还可将正幸福度按规则转成全局产出，也不是所有文明默认享有。既有 GoldenAgeManagerTest 验证了积累、减少、不低于零和持续时间等行为。

4. 文明回合结束时，净流量才进入国库

本地 TurnManager.kt结束结算顺序 · L275

① 普通文明先刷新，再取当前预测对象。刚进入本方行动阶段时看到的数字，可能已经被之后的建造、贸易、单位变化改写；这里重新读取。

② 若进入严重赤字解散单位的分支，单位移除会更新维护费，局部变量也会改取新统计。本例国库为正，不进入此分支。

③ 文明黄金总净流量先 toInt()，再交给 addGold。9.75 变成 9；−2.75 变成 −2。没有保存小数尾数供下一次凑整。

④ 黄金入账后才开始各城结束处理，包括生产进度累加和人口增长。若城市此时增长并改变统计，不会回头补算本次已经入账的黄金。

⑤ 接着处理临时规则和黄金时代。随后还有单位、外交等阶段，所以方法结束后的预测读数不一定等于刚才入账使用的数值。

与上一课比较取整位置：普通生产是城市最终生产力 roundToInt()，12.4 → 12、9.5 → 10；黄金则把文明总净流量 toInt()，9.75 → 9、−2.75 → −2。黄金不是每个城市分别取整后再相加。不过，建筑和单位维护费在各自的计算阶段已经有取整，不能把所有费用都拖到最后统一处理。

// Civilization.addGold 完整方法，调整折行。
fun addGold(delta: Int) {                         // ① 整数变化量
    gold = when {
        delta > 0 && gold > Int.MAX_VALUE - delta ->
            Int.MAX_VALUE                       // ② 防止上溢
        delta < 0 && gold < Int.MIN_VALUE - delta ->
            Int.MIN_VALUE                       // ③ 防止下溢
        else -> gold + delta                    // ④ 正常加到余额
    }
}

addGold · L1030gold 的私有 setter · L146

① 参数可以为正，也可以为负。gold 可以公开读取，但 setter 是私有的，外部通过这个方法修改。

② 增加过大的数值时，封顶到整数上限，避免溢出成负数。

③ 减少过大的数值时，封底到整数下限。这里保护的是整数范围，并没有把负国库截成 0。

④ 一般情况就是 gold + delta。本例 100 + 9 = 109；若余额 1、净流量 −2.75，则本次变为 1 − 2 = −1。

顶栏也明确读取两个字段：goldLabel 读取 civInfo.gold，goldPerTurnLabel 读取 statsForNextTurn.gold。UI 展示不会调用 addGold。购买、出售、掠夺等一次性黄金变化还有各自调用路径，所以“本节的每回合收支在结束时结算”不代表国库只允许在结束回合时变化。

顶栏分开读取余额与净流量 · L124

扩展：负净流量、负国库与强制解散单位，不是同一个条件

getStatMapForNextTurn 在道路、单位等费用之后检查：当时已汇总的黄金净值小于 0，且当前国库 gold < 0，才加入 Treasury deficit 科学负值。差额为 max(当时的黄金净值, 1 − 当时的科学总值)，目的是让该步处理后的科学至少保留 1。注意源码顺序：这项检查在 Trade 和全局规则来源加入之前，不能简单改述为“最终顶栏净收入为负就扣科学”。

无贸易和其他全局效果时，净黄金 −2.75、科学 10、国库 1，不扣科学；先结算黄金后国库成为 −1，下一次刷新才算出科学 7.25。若每回合赤字扩大到 −29.75，则该步科学降至 1。这些数字已用真实方法验证。

强制解散单位是另一个分支，位于黄金入账之前：gold <= −200 且 nextTurnStats.gold.toInt() < 0，才循环选择军事单位解散，直到条件不满足或无军事单位可解散。因为判断在本次入账前，若本次扣款才让国库跌过 −200，不会在刚才已经经过的位置立刻再判一遍。本课不展开解散退款与排序细节。

移除单位也刷新维护费 · L176

Godot tip：把收支预览和实际余额分开

做城池经营或门派经营时，可以让费用预览从当前城市、建筑和人员状态计算，让固定结算阶段修改余额。这样 UI 多次请求刷新，不会重复收取薪资或税金。若采用即时制，应明确按哪个时间步、怎样保留小数结余；Unciv 的整数回合入账规则需要重新设计。这里讨论数据与结算职责，不要求实现 Godot 工程，也不依赖某个节点回调来保证结算只执行一次。

心智模型

  • 文明按来源合并各城的 finalStatList。城市已经计算过的建筑维护费随明细进入，单位和道路等费用再在文明层加入。
  • statsForNextTurn 是当前预测，gold 是实际余额。重复刷新只替换统计对象；每回合黄金通过结束阶段的 addGold 入账。
  • 单位费看数量、免费名额、折扣和时间，再取整数。新增单位参与计算，但不保证整数费用立即上升。
  • 幸福度单独汇总，跨规则边界时重算城市。增长与生产受到的影响由当前规则和条件决定，不能只套用“负幸福度”一个判断。
  • 先结算文明黄金，再推进城市生产与人口。普通新单位下次开始时生成，刷新未来收支，后续结束时才按当时净值影响国库。
