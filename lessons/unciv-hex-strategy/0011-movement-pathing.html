第二阶段 / 地图专题 · 地图的使用第一课

移动代价与寻路

地图生成专题（07～10 课）到上一课为止：地图上有了地形、山川、河流、起点和资源，但它是静态的。从这一课起转向“地图怎么被使用”——最先碰它的就是单位移动。选中一个单位时界面高亮的那些格子、点远处一格时单位脚下出现的路线，背后是同一套问答：从这格到那格要花多少移动力？哪些格子根本走不过去？跨很多回合时哪条路最省？读完你应当能拿一张小地图，亲手推演出一个单位的可达范围和一条最短路径。

需要的基础：第五课的邻居偏移表与 getDistance（寻路的“一步”就是邻居）、zeroBasedIndex（寻路缓存的数组下标）；第六课的地形/特征分层（movementCost 查的是 lastTerrain，即特征压过基础地形）。源码版本：1df6249a41301056ddc4448a95a93ddf5403e061。

目标、回顾与场景

三个场景都来自玩一局的操作。场景一：选中一个还有 2 移动力的勇士，界面把周围一部分格子标成高亮——为什么高亮到某圈为止、有的近格反而不亮？这是第 2 节的可达图。场景二：让工人从首都走到 20 格外的分城，单位不是沿直线爬过去，而是拐了个弯——它绕开的是什么、在省什么？这是第 3 节的跨回合路径。场景三：同一条路，没发明机器前每格 0.5 移动力、发明后变 0.33，铁路则是 0.1——为什么寻路器要为这些小数专门换一套整数算术？这是第 1 节的代价表与第 4 节的定点数。

本课的三个问题

  • 代价：走一步的移动力由哪几层决定？100f 这个特殊值是什么意思？
  • 可达：“这回合能到哪”与“能不能停在这”为什么是两个问题？
  • 路径：跨回合寻路优化的是移动点总和还是回合数？两条算法线怎么分工？

读完还要会一件事：不看正文，在一张纸上画出 3～4 格的小地图，标出移动力 2 的单位一回合能到的所有格子，并对“为什么某格到不了”给出源码依据。

1. 一步多少钱：代价的五个来源

寻路的一切都建立在“一步多少代价”上。这里的一步，指从一格走进相邻的六格之一——第五课的邻居偏移表给出六个方向，本课给每个方向标价。代价查询的总入口是 MovementCost.getMovementCostBetweenAdjacentTiles，它按固定顺序过一遍所有规则，先命中先返回：

// MovementCost.getMovementCostBetweenAdjacentTiles（部分代码）。问：走一步收多少钱？
fun getMovementCostBetweenAdjacentTiles(
    unit: MapUnit, from: Tile, to: Tile, ...
): Float {
    if (unit.cache.cannotMove) return 100f                        // ① 不能动：标价 100

    if (from.isLand != to.isLand && unit.baseUnit.isLandUnit
        && !unit.cache.canMoveOnWater)
        return if (from.isWater && to.isLand)
            unit.cache.costToDisembark ?: 100f                     // ② 登陆/上船花光
        else unit.cache.costToEmbark ?: 100f

    if (considerZoneOfControl &&
        isMovementAffectedByZoneOfControl(unit, from, to))
        return 100f                                                // ③ 控制区：花光

    if (unit.cache.allTilesCosts1) return 1f                       // ④ 全图代价 1 的单位

    val extraCost = ...                                            // ⑤ 敌方移动惩罚，先记着

    if (from.getUnpillagedRoad() == RoadStatus.Railroad
        && to.getUnpillagedRoad() == RoadStatus.Railroad)
        return RoadStatus.Railroad.movement + extraCost            // ⑥ 两端铁路：0.1

    val areConnectedByRoad = from.hasConnection(civ) && to.hasConnection(civ)
    ...
    if (areConnectedByRoad && (!areConnectedByRiver
        || civ.tech.roadsConnectAcrossRivers))
        return civ.tech.movementSpeedOnRoads + extraCost           // ⑦ 道路：0.5 或 1/3

    if (unit.cache.ignoresTerrainCost) return 1f + extraCost       // ⑧ 无视地形
    if (areConnectedByRiver) return 100f                           // ⑨ 涉河无路：花光

    val terrainCost = if (to.isCityCenter()) 1f
        else to.lastTerrain.movementCost.toFloat()                 // ⑩ 地形代价
    ...
    if (to.terrainFeatures.any { hasDoubleMovement(unit, it, ...) })
        return terrainCost * 0.5f + extraCost                      // ⑪ 双倍移动减半

    ...
    return terrainCost + extraCost                                 // ⑫ 兜底：地形原价
}

这段像一个收费站层层设卡的脑内模型：从特殊状态查起（不能动、上下船、控制区），再按“路优先于地形”的顺序逐层放行，任何一层报出价来就直接返回，后面不再看。

① cannotMove 是单位级缓存（ fortified 之类状态之外的各种“这回合动不了”），直接标 100。100f 不是精确价格，而是一个“大到等于花光全部”的哨兵值——移动力再高的单位也不会超过几十，100 确保这一步在比较时永远最差。后面 ③⑨ 的 100f 同理。

② 陆地单位水陆切换（上船/下船）默认也花光；只有规则给了折扣（costToEmbark/costToDisembark）才便宜。 embark 译作“登船”，disembark 译作“登陆”。

③ 控制区（Zone of Control，ZoC）：敌方军事单位与敌城压着周围六格，在它的阴影里“从一格挪到另一格”直接花光全部移动力。判定只看 from 和 to 的公共邻居里有没有压着的敌人（anyTilesExertingZoneOfControl），海军的 ZoC 对陆海都生效。

④ 带 “All tiles cost 1 move” 类 unique 的单位（如侦察兵升级）全图每格代价 1，路都不看。

⑤ extraCost 是敌国领土对敌军的额外加价（“Enemy units spend extra movement”），先算好、之后每层出口都带上它。

⑥ 铁路要求两端都是未劫掠的铁路格，0.1 一格——这是全游戏最快的路。注意用的是 movement 而非 movementImproved（后者 1/3，是给“道路升级到铁路”的寻路提示用的，第 4 节会见到）。

⑦ 道路：两端都在 hasConnection(civ) 的路网上，且要么不涉河、要么研究了“道路跨河”科技，价格取 civ.tech.movementSpeedOnRoads——默认 0.5，研究机器（Machinery，挂 RoadMovementSpeed）后变 1/3。注意这个字段是文明的而非单位的：全文明共享道路速度。

⑧ “Ignores terrain cost” 单位（如 Scouter）按每格代价 1 走，不吃森林丘陵的加价。

⑨ 渡河：from 与 to 隔一条河（第九课的河流边存储在这是判定依据）且没有跨河道路——整个回合花光。这就是“贴着河的格子难打”在移动层的体现。

⑩ 地形代价查 to.lastTerrain.movementCost——lastTerrain 是第六课讲过的“最顶层地形”：有特征取特征（Hill 2、Forest 2、Jungle 2、Marsh 3），否则取基础地形（草原/平原/沙漠/冻土/雪原都是 1）。城市中心按代价 1 算。REPL 实测（G&K 规则集）：代价不是 1 的只有 Hill 2、Forest 2、Jungle 2、Marsh 3、Fallout 2。

⑪ 双倍移动（Double movement in [terrain]）把地形价砍半，如森林里的弓手升级。按特征、基础地形、过滤符三层各查一遍（此处只列特征层）。

⑫ 兜底：地形原价 + 敌境加价。整段的关键是顺序：铁路 > 道路 > 双倍移动 > 地形，且特殊状态（不能动、ZoC、渡河）永远优先压住一切。

Godot 对照：代价函数就是“边的权重”

这套判定链在你的游戏里就是邻接图的边权函数：输入 (from, to, unit, 全局状态)，输出一个非负数。Unciv 的可借鉴点是把规则放进数据、把顺序写死在代码里——movementCost 存在 Terrains.json、道路速度存在科技 unique 里，代价函数只负责按优先级组合。Godot 4.x 里把单位移动做成 AStar2D/AStarGrid2D 时，_compute_cost 回调正好放这条链；哨兵值 100f 的技巧（用超大代价表示“事实上的不可行”）在引擎自带的 A* 里同样可用，比抛异常省心。注意 Godot 的 AStarGrid2D 是方格的，六边形要么用 AStar2D 自建点集，要么用 Polygon（第 28 课会汇总比较）。

2. 这一回合能到哪：可达图

知道每步的价格，就能算“这回合能到哪”。老实现（当前默认设置仍在用）是一个按层松弛的过程，入口 UnitMovement.getMovementToTilesAtPosition；A* 新实现（第 4 节）语义相同。先看老实现，因为它把语义讲得最直白：

// UnitMovement.getMovementToTilesAtPosition（部分代码）。问：还剩 2 点力，能到哪些格？
val distanceToTiles = PathsToTilesWithinTurn()
distanceToTiles[unitTile] = ParentTileAndTotalMovement(unitTile, unitTile, 0f)   // ① 起点代价记 0
if (unitMovement == 0f || unit.cache.cannotMove) return distanceToTiles          // ② 没力：只剩起点

var tilesToCheck = listOf(unitTile)
while (tilesToCheck.isNotEmpty()) {                          // ③ 一轮处理一层
    val updatedTiles = ArrayList<Tile>()
    for (tileToCheck in tilesToCheck) {
        val tileToCheckMovement = distanceToTiles[tileToCheck]!!.totalMovement
        for (neighbor in tileToCheck.neighbors) {
            var totalDistanceToTile: Float = when {
                !neighbor.isExplored(unit.civ) ->
                    tileToCheckMovement + 1f                  // ④ 迷雾格猜作平地（代价 1）
                !canPassThroughCache.getOrPut(neighbor.zeroBasedIndex) {
                    canPassThrough(neighbor) } -> unitMovement    // ⑤ 过不去：标满价
                else -> {
                    val movementCost = movementCostCache.getOrPut(key) {
                        MovementCost.getMovementCostBetweenAdjacentTilesEscort(...) }
                    tileToCheckMovement + movementCost        // ⑥ 正常计价
                }
            }
            val currentBestPath = distanceToTiles[neighbor]
            if (currentBestPath == null
                || currentBestPath.totalMovement > totalDistanceToTile) {   // ⑦ 松弛：找到更便宜的路
                if (totalDistanceToTile < usableMovement - Constants.minimumMovementEpsilon)
                    updatedTiles += neighbor                 // ⑧ 还有富余：继续从这扩散
                else
                    totalDistanceToTile = usableMovement      // ⑨ 超了：钉在满价
                distanceToTiles[neighbor] =
                    ParentTileAndTotalMovement(neighbor, tileToCheck, totalDistanceToTile)
            }
        }
    }
    tilesToCheck = updatedTiles
}

脑内模型是水波扩散：从起点荡开一圈圈涟漪，每个格子记录“到我这里最便宜的累计水花”；只要还有富余移动力，涟漪就继续往外传。

① 起点自己记代价 0，父格指向自己——这是后面回溯路径的终止条件。

② 移动力为 0 或缓存说不能动，直接返回只有起点的表。注意两个容易混的判定：canMoveTo（能不能停在这）与 canPassThrough（能不能路过这里）是两回事——友方单位的格子能路过不能停（除非换位），敌城不能停但攻击目标格要标成“可达”才能被选中。

③ 外层 while 一轮处理“上一轮新解锁的格子”，像 BFS 按层推进；但每格的 totalMovement 是真实代价累加，不是层数，所以丘陵那边的“层”传得近、平地那边传得远。

④ 迷雾里的格子一律猜作代价 1——玩家没见过它的真实地形，就当是平地。半路撞上山再修正，moveToTile 里有对应的中断重算。

⑤ canPassThrough 过不去的格子（敌军占着、封闭国境、不可通行地形）标成 unitMovement 满价——注意不是不记录！源码注释点明原因：算“怎么打到敌人”时必须假设敌人那格可达，否则所有攻击寻路都会失灵。所以满价是“这格算你能到，但到了就别想再走”。

⑥ 正常情况查第 1 节的代价函数。Escort 版本会取单位与其护卫（escort，两两绑定的成对单位，如工人+勇士）中更贵的那个价——一对人马按腿短的那条腿走。

⑦ 松弛：如果这次算出的累计价比已记录的便宜，就更新。同一格可能从多个方向被触及，留下最便宜的方向作为 parent。

⑧ 还有富余（差值大于浮点容差 minimumMovementEpsilon）的格子进下一轮扩散。

⑨ 超预算的格子仍然记录，但价格钉在 usableMovement——这就是“ Civ V 里哪怕只剩 0.1 移动力，相邻一格也能挤过去、然后力尽”的实现：格子有记录（可点），价格显示为满。usableMovement 是自己与护卫移动力取小后的可用值。

REPL 实测一张半径 8 六边形图（217 格）：移动力 2 的单位从原点出发，可达 19 格——起点 1 + 一环 6（各耗 1 点）+ 二环 12（平地各耗 2 点）；在 (0,1) 放一个丘陵特征后，(0,1) 本身仍可达（1+2=3 超了？不——⑨ 的钉价规则让它记 2.0 满价，仍出现在结果里），而穿过它去 (0,2) 就彻底没了：丘陵后面那格连记录都不该有……实测正是如此，(0,2) 不在表里，其余二环 11 格照常可达（共 18 格）。把移动力换成 1.5 再测：一环照常（各耗 1 点），丘陵格 (0,1) 记 1.5 满价，平地二环格照常 1.5 钉价可达——18 格。这两个数字建议你自己在纸上推一遍，是本课练习 A 的原型。

3. 跨回合的最短路：路径

可达图回答“这回合”，路径回答“这局”：目标在 20 格外，单位要分好几个回合走完。UnitMovement.getShortestPath 的老实现是按回合长树：每一轮先算出本回合的可达图，从边缘挑出下一回合的出发点，直到够到目标：

// UnitMovement.getShortestPath 的主循环（部分代码）。问：好几回合的路怎么长出来？

val movementTreeParents = HashMap<Tile, Tile?>()    // ① 回合树：这格从哪格跳来的
movementTreeParents[currentTile] = null

val visitedTilesBitset = BitSet(currentTile.tileMap.tileList.size)   // ③ 老格子不再当出发点
visitedTilesBitset.set(currentTile.zeroBasedIndex)

while (true) {

            getDistanceToTiles(true, passThroughCacheNew, movementCostCache)
        else getMovementToTilesAtPosition(          // ⑤ 每个出发点各算一次单回合可达
                tileToCheck.position, unitMaxMovement, false,
                visitedTilesBitset, passThroughCacheNew, movementCostCache)

        for (reachableTile in distanceToTilesThisTurn.keys) {
            if (avoidDamagingTerrain &&
                unit.getDamageFromTerrain(reachableTile) > 0) continue   // ⑥ 第一遍避开伤地
            if (reachableTile == destination) {
                val path = mutableListOf(destination)     // ⑦ 够到了：回溯成列表
                var intermediateTile = tileToCheck
                while (intermediateTile != currentTile) {
                    path.add(intermediateTile)
                    intermediateTile = movementTreeParents[intermediateTile]!!
                }
                path.reverse()
                return path
            }
            if (movementTreeParents.containsKey(reachableTile)) continue  // ⑧ 先到先得
            if (!canMoveToCache.getOrPut(reachableTile) { canMoveTo(reachableTile) })
                continue                                  // ⑨ 不能停的格不当出发点
            movementTreeParents[reachableTile] = tileToCheck
            newTilesToCheck.add(reachableTile)
        }
    }
    if (newTilesToCheck.isEmpty()) return emptyList()     // ⑩ 扩不出去：无路
    for (tile in newTilesToCheck) visitedTilesBitset.set(tile.zeroBasedIndex)
    tilesToCheck = newTilesToCheck.filterNot { tile ->
        tile.neighbors.all { visitedTilesBitset.get(it.zeroBasedIndex) } }  // ⑪ 只留边缘
    distance++
}

脑内模型是把一张登记卡压进一个长整数的行李箱：每样信息占固定的几个比特，按“越靠左越优先”排座次，比较优先级时直接比较整个 Long——不用拆箱、不用分配对象。

① 缓存键三元组：单位在哪、还剩多少力、满力多少。任何一项变了（走了、动了），整张缓存作废重来。所以 A* 缓存只在“单位不动连续询问”时命中。

② 20 位下标正好覆盖第五课的 zeroBasedIndex（最大图 748501 格 < 2^20）。缓存本体是 LongArray(tileList.size)，按 zeroBasedIndex 直接寻址——第六课的 tileList 顺序在这里变成了数组布局。

③ 邦交分 8 档存在 3 位里，存的是 (7−ordinal)，盟友=0 最优——平局时优先走朋友的地。

④⑤⑥ 移动力用 base-30 定点数存：1.0 = 30。为什么是 30？铁路 0.1 = 3/30、道路 1/3 = 10/30——这两个分数在 base-30 下都是精确整数，浮点数 0.1+0.2≠0.3 的经典麻烦被彻底绕开。REPL 实测：fpmFromMovement(3.666f).bits = 110（= 3×30+20），读回 3.6666667；FPM_ONE.bits=30、FPM_POINT_FIVE.bits=15。9 位最多存 511/30≈17.0 移动力，正好覆盖原版最快的单位加双倍移动。

⑦ 父格不存坐标存钟点方向（第五课的 6 个邻居方向，偶数所以 /2 存 3 位）——回溯时从当前格按钟点取邻居即得父格，20 位坐标省成了 3 位。

⑧ canMoveTo 一位：这格是“能路过”还是“能安家”。

⑨ damagingTiles 是全字段最高位：宁可绕远也不掉血的路线永远优先，只有实在绕不开才允许“带伤路线”赢——这正是老实现要跑两遍（先避损后放行）的逻辑，A* 把它变成了优先级的一部分。只记 0～3，2 位封顶。

脑内模型是导游估时：每个格子排队时带着“已花时间 + 到终点最快也要多久”的估计，总估计最短的先被展开；估计永远不夸大（可采纳启发式），所以先展开到的路线一定是真最短。

① 已花 = 回合数 × 满力 + 本回合已用。用“满力”折算回合数是关键：一个回合不管走没走满都算一整个回合的预算，这与“优化回合数”的目标一致。

② 预估 = 几何距离（第五课的 aerialDistanceTo）× 0.1——假设剩余每一格都是铁路。这是物理下限：任何路的单格代价都不可能低于铁路，所以这个预估永远不会高估，A* 的正确性由此保证。源码注释还解释了为什么不取 0（纯 Dijkstra）：取 0 也能对但慢得多；也不能高于 0.1，否则会错过“绕远坐铁路”的最优解——第 3 节那条 14 格铁路环线正是靠 0.1 的预估才赢过 3 格直路的。

③ todo 是 LongPriorityQueue：PrioritizedNode 把预估总代价塞进 RouteNode 的高位，比较时整个 Long 直接比——damagingTiles 在最高位，所以“不掉血”永远压过“便宜”；同为不掉血时比预估，再比邦交、比回合。一次堆操作零对象分配。

取舍：先语义后引擎

这一课的阅读顺序本身就是 Unciv 的开发顺序：先把“一步多少钱、能到哪、几回合到”的语义用最直白的代码写对（老实现几乎就是伪代码），再为性能重写引擎（A* + 位域 + 定点数），全程用同一组测试钉住语义。反过来先写引擎再补语义，通常得到一个“快但没人说得清它算的是什么”的寻路器。做自己的游戏时同样建议先写朴素 BFS 版本验证规则手感（代价表调起来才知道好不好玩），引擎优化放在数值稳定之后。两套并行的灰度切换在单机游戏里显得隆重，但“测试按算法参数化双跑”这个习惯在任何项目里都划算。

心智模型

  • 一步的价钱按固定顺序判定：不能动/上下船/ZoC 的 100f 哨兵 → 铁路 0.1 → 道路 0.5 或 1/3 → 双倍移动减半 → 地形原价；lastTerrain 决定地形价（Hill/Forest 2、Marsh 3、平地 1）。
  • 可达图是水波扩散：每格记最便宜累计价与来向；过不去的格记满价（攻击寻路要用），超预算的格钉满价仍可达（相邻格总能挤过去）。
  • “能过”与“能停”是两个问题：canPassThrough 管借道，canMoveTo 管安家；友军格能停、中立平民老实现能穿、敌军敌城只能“到”。
  • 跨回合路径按回合数优化：每轮从可达边缘长一截树，返回值只含每回合落点；绕远铁路能赢过直路（A*），丘陵直穿能赢过平地绕行（按天数）。
  • A* 引擎三件套：缓存键（位置+余力+满力）管失效、RouteNode 塞进一个 Long（伤血最高位、邦交当平局裁决、父格存钟点）、base-30 定点数让 0.1 和 1/3 都精确。
  • 预估 = 几何距离 × 铁路价 0.1 是物理下限，保证 A* 正确还不慢；两代实现同名入口、测试双跑，语义被测试钉死而不是被注释描述。

选择题答案与核对位置

1：按地形价扣两点；2：能路过不能停；3：直穿只要三回合；4：铁路价当每格下限。分别对应 代价判定链、可达图的能过能停、回合数优先、A* 启发式。

练习 A · 手推一张可达图（10 分钟）

一张无限平地图，单位站在 O，移动力 2，东边相邻格 H 是丘陵，H 的东边相邻格 F 是平地（其余方向全是平地）。① 列出本回合可达的所有格子（以“相对 O 的方位 + 环数”描述）与各自的 totalMovement。② H 格的 totalMovement 是多少？它为什么出现在结果里？③ F 格（H 后面那格）在不在结果里，为什么？④ 若单位移动力是 1.5，H 与 F 的结论变不变？

展开核对要点

① 一环 6 格各耗 1 点；二环平地 11 格（除 H 东边的 F 外共 11 格：H 方向只有 F 一格被挡）各耗 2 点。合计 O + 6 + 11 = 18 格——与 REPL 实测的丘陵场景完全一致（217 格图 18 格）。② H 的真实累计 1+2=3 超了 2，按钉价规则记 usableMovement=2.0 仍入表——这就是“ Civ V 相邻格总能挤过去”的实现。③ F 不在：到 F 必须经过 H，而 H 已记满价、不再作为扩散源（updatedTiles 不含 H）。④ 1.5 时：一环照常各耗 1 点；H 钉 1.5 仍可达；F 仍不可达（H 不扩散）。REPL 实测两场景均为 18 格，H 记满价、F 无记录。

练习 B · 算一条跨回合路径（8 分钟）

单位移动力 3，站在 (0,0)，目标 (0,4)。(0,1)、(0,2) 是丘陵，其余全平地，无道路。① 直穿路线每回合怎么走、几天到？绕行路线（避开两格丘陵）几天到？② getShortestPath 返回的列表里有哪几个坐标？为什么不是每一步都在里面？③ 若把移动力改成 5，到达后剩几点力？

展开核对要点

① 直穿：第 1 天 3 点走 (0,1)H 2 + (0,2)H 2 超了？——3 点走一格丘陵 2 剩 1，第二格丘陵 2 挤过去力尽停 (0,2)；第 2 天 3 点走 (0,3)1 + (0,4)1 到达，共 2 天。绕行：每格代价 1，从 (1,1) 方向绕约 6 格，也是 2 天。直穿不劣。② REPL 实测返回 [(0,2), (0,4)]：列表只含每回合落点（(0,2) 是第一天过夜处），中间步 (0,1)、(0,3) 由 moveToTile 按单回合可达图补全——getShortestPathReturnsOnlyEndOfTurns 测试钉的就是这个语义（同场景返回 2 元素）。③ 移动力 5：5−2−2=1 剩 1 点正好走 (0,3)，第 2 天 5−1=4 点余裕到达。REPL 实测（maximizeRemainingMovementWhenReachingDestination 场景，目标 (0,3)）currentMovement = 1.0。

练习 C · 判定链插队（5 分钟）

把下面四个情形按代价函数的判定顺序排出来，并说出各自命中的层与价格：A 两端铁路格；B 有道路连接但隔河（未研究跨河科技）；C 带无视地形的侦察兵走进丛林；D 移动力 0 的单位尝试移动。

展开核对要点

顺序 D → B → A → C（按命中先后）：D 最先被 cannotMove 拦住，100f；B 在道路判定处被 areConnectedByRiver 拦下（道路层要求 !areConnectedByRiver || roadsConnectAcrossRivers），落到渡河层 100f；A 在铁路层命中 0.1（注意铁路判定在道路之前）；C 的 ignoresTerrainCost 在道路之后、渡河之后，1f。这道题的重点是“顺序即语义”：C 如果有铁路可坐仍按铁路走（无视地形不吃铁路），D 无论地图怎样都动不了。
