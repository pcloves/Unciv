# 学习背景与教学偏好

确认日期：2026-09-09。背景为学习者自述，尚未做能力测评。

## 背景

- 资深 Java 开发者，有约 6 个月 Kotlin 使用经验。
- 有约 2 年 Godot 4 C# 使用经验，偏 2D、TileMap 和 UI；3D 经验较少。
- 了解《文明》类玩法，但游玩不多；人口、产出和结算细节需随课解释。

## 教学约定

- 中文教学；保留 Kotlin/C# 标识符，先建立整体，再深入局部。
- 重点是读懂项目；多用短代码及机制注释，控制连续长篇解释。
- Godot 对照用 tip，明确相似性与边界；不默认安排 Godot 项目实现作业。
- 欢迎与本课相关的生产经验、配置、排障、性能和设计取舍 callout。
- 每课主动回指已学概念，每课正文后、检索练习前设置“心智模型”。
- 每课正文、源码走读和检索练习合计约 40～60 分钟；可选扩展另计。
- 面向 2K 显示器提供较宽布局，兼顾系统缩放、移动端和打印。
- 配对代码块每行控制在约 100 半角字符宽以内（含行尾注释），超出按 Kotlin 续行惯例折行，避免水平滚动条。
- 教材正文独立于对话，其他有相近基础的开发者也应能阅读。
- 全部教学文件放在 `lessons/`；跨课程内容共享，专项内容按课程目录隔离。

## 中文写作要求

- 读者是母语为简体中文的游戏程序员。用自然的中文技术文章写法，像向同行讲清一段实现，减少模板化总结、翻译腔和生造术语。
- 优先写清楚“谁在什么情况下做什么、为什么这样做”。能说“切换游戏界面”，就不要用“发布结果”让读者猜实际动作。
- 保留字段、引用、缓存、线程等常用技术词。项目特有概念第一次出现时，用具体游戏场景解释，并给出代码里的名字；不要为了口语化牺牲准确性。
- 代码注释要帮助读者理解行为或原因。只有部分源码时，直说“相关字段”“部分代码”“省略其他字段的复制”；多段代码放在一起时标清各自所在的方法。
- 先讲具体机制，再归纳概念。不要让读者先理解一个抽象说法，再去源码中猜它是什么意思；也不要把技术文章改成刻意随意的聊天口吻。
- 配对排版时，左侧一段代码摘录只配右侧一段讲解，讲解严格按代码从上到下的顺序进行；多段代码各自标注所在方法，参数、分支的说明要落到对应代码行上。抽象总结放到配对块之后单独成段，不要混在逐行讲解里。
- 交稿前按中文读者的习惯通读正文、标题、注释、题目和答案，检查指代、因果和术语是否一致。
- 第六课反馈：解释不清时先整理因果顺序，不靠增加篇幅解决。坐标推导使用成对、同层次的术语；优先用简短的代入计算说明“什么不变、什么改变”，再接一个例子和源码。
- 第八课反馈：createXxx 类源码函数名首次出现时，先交代它对应的界面选项或调用场景（如地图类型下拉框），再讲行为。表格先说明每列在比什么、行按什么分组、每组预期形态，再放数据。两种做法对比时，每边都要给“什么时候用”的判据和一个代入例子，不能只给结论式的一句话。
- 第九课反馈：`baseTerrain` 统一译作“基础地形”（第六课原用词），不用“底地形”；已收入 architecture.html 常用术语表（#base-terrain）。数值表格交稿前逐格复算；方向性表述（“更接近 0”之类）用一个代入数字自检。修订段落时同步检查配对编号是否仍一一对应。
- 2026-09-18 反馈：不要为了“简化”而创造母语者不使用的课程术语，例如“主算例”“派工地”“派工草地农场”“工位”“柜台”“招聘”。应直接说“下面这个例子”“人口正在工作的地块”“有农场且分配了一个人口的草地”“安排人口”。选择题选项也不要求字数相同，优先自然、完整、没有凑字痕迹的中文；同步更新 `lessons/README.md` 与 `check-course.cjs`。
